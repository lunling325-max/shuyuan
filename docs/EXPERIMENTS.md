## E-001　语义去重的可行性标定

**日期**：2026-10-31　**脚本**：`scripts/dedup_probe.py`、`similarity_curve.py`、`normalize_probe.py`

**问题**：官方用例 3.1 要求系统"基于文本语义内容而非文件名"检测重复。那么文本相似度到底能不能用？阈值怎么定？

**方法**：PyMuPDF 抽取全文 → 归一化 → 计算 k-gram shingle 的 Jaccard 相似度。

### 第一轮：天真做法，失败

| 指标 | v1 vs v7（同一篇·不同版本） |
|---|---|
| 字符集 Jaccard | 0.9620 |
| 5-gram Jaccard | **0.6836** |

0.68 会被任何合理阈值判成"不同论文"，**系统会直接漏掉官方测试用例**。

### 第二轮：定位根因

| k | 1 | 2 | 3 | 5 | 8 |
|---|---|---|---|---|---|
| Jaccard | 0.8805 | 0.7951 | 0.7547 | 0.6836 | 0.5887 |

单调下降 → 词在，顺序/切分乱了。查词频差异发现 v1 独有高频词是 `signi(+6)`、`cantly(+5)`、`rst(+4)` —— 全是残片，不是真词。

**根因**：
1. **连字字符**：v1 含 35 个 U+FB00–FB06（`ﬁ`×31、`ﬂ`×4），v7 含 **0 个**。`ﬁrst` 的 `ﬁ` 不在 `[a-z]` 里 → 变成 `rst`。
2. **行尾断词**：`signi-\ncantly` 被切成两段。

### 第三轮：归一化后重新标定

归一化 = `NFKC`（拆连字）+ 去除行尾连字符 + 折叠空白 + 小写。

| 指标 | 原始 | 归一化后 |
|---|---|---|
| unigram Jaccard | 0.8844 | 0.9054 |
| 5-gram Jaccard | 0.6819 | **0.7237** |
| 词袋重合 | — | 0.9068 |

### 第四轮：判别力标定（关键）

| 对比 | k=3 | k=5 | 真值 |
|---|---|---|---|
| v1 vs v7 | 0.7848 | **0.7237** | 同一篇·不同版本 |
| v1 vs BERT | 0.0166 | 0.0039 | 不同论文 |
| v7 vs GPT-3 | 0.0080 | 0.0018 | 不同论文 |
| BERT vs GPT-4 | 0.0084 | 0.0011 | 不同论文 |
| GPT-3 vs GPT-4 | 0.0199 | 0.0059 | 不同论文 |

**同类与异类相差 100 倍以上**，判别力绰绰有余。

### 结论（写进设计）

1. **阈值**：`k=5 Jaccard > 0.30` 判为"同一篇文献的疑似重复"；`< 0.05` 判为"不同文献"。中间灰区（0.05–0.30）交给 arXiv ID / 标题 / 摘要做二次确认。
2. **归一化是必须的，不是可选的**。不做 NFKC + 断词修复，官方用例直接判错。
3. **真正的难点不在"是否重复"，而在"重复的三态判别"**：
   - 完全相同（byte-identical）→ 拒绝并提示
   - 同一篇不同版本 → 版本谱系 + 差异摘要 ← **这是拿分点**
   - 不同文献但高度相似（同作者系列）→ 提示但不拦截
4. **性能**：5950 个 5-gram × 每对比较，100 篇文献两两比较约 5000 次，纯集合运算毫秒级。超过 1000 篇再上 MinHash/LSH，当前规模不需要。

### 踩坑记录

- PyMuPDF 用 `import pymupdf`，`import fitz` 已废弃（会告警）。
- Windows 控制台默认 GBK，输出非 ASCII 会抛 `UnicodeEncodeError`，需 `PYTHONUTF8=1`。
- PyPI 的 `files.pythonhosted.org` 在本机不可达，必须走清华镜像 `https://pypi.tuna.tsinghua.edu.cn/simple`。

## E-002　引用校验守卫（Citation Guardrail）

**日期**：2026-10-31　**模块**：`apps/api/app/guardrails/citation.py`、`apps/api/app/parsing/text_index.py`
**测试**：`apps/api/tests/test_guardrail.py`（9 条）

### 问题起点：我们自己的 Agent 先编了

让 DeepSeek 生成 v1→v7 版本修订摘要，人工抽样核查 5 条结论：

| LLM 结论 | 真实情况 | 判定 |
|---|---|---|
| "代码可用性改为给出 tensorflow/tensor2tensor 地址" | 该字符串当时只出现在致谢 | ❌ 错配 |
| "新增标签平滑 εls=0.1 的说明" | v1 原文就有 `label smoothing of value εls = 0.1` | ❌ 编造 |
| "新增 FFN 等价两个卷积的描述" | 两版均未找到 | ❌ 未证实 |
| 新增致谢段落 | 属实 | ✅ |
| dmodel=512 / 内层 2048 | 属实 | ✅ |

**根因**：喂给模型的差异块被截断到 150 字符，块间还混着图注，模型只能靠猜补缺口。

### 设计

1. **词级坐标索引**：`page.get_text("words")` → (归一化 token, 页码, bbox) 词流。
2. **归一化**：NFKC 拆连字 + 小写 + 去标点。不做这一步，v1 的 `conﬁguration` 永远匹配不上 `configuration`。
3. **三级匹配**：逐字 → 截断容错 → 模糊（稀有词剪枝，避免 541 页全文滑窗）。
4. **判定**：`supported`（全逐字）/ `weak`（仅模糊）/ `unsupported`（全不中，直接丢弃）。

### 调优过程中被测试抓住的两个 bug

| 现象 | 原因 | 修复 |
|---|---|---|
| 真结论被误杀（Google 授权声明） | 模型在 150 字符处把引用截断成 `journalis` | ① 喂给模型的证据不再截断 ② 加入截断容错 |
| 篡改引用被判为"逐字命中" | 截断容错太粗，`tensor2tensor-api-v2` 砍掉尾巴后匹配成功 | 被丢弃的尾部必须是原文紧接着那个词的**前缀**，否则判编造 |

第二个 bug 尤其危险：它等于给幻觉开了后门 —— 真句子 + 编造尾巴可以一路绿灯。

第三个 bug 是后来换到 BERT 才暴露的，也是最难自己看出来的一个：

| 现象 | 原因 | 修复 |
|---|---|---|
| BERT 上真结论 3 条**全部**判 unsupported | 索引按 PDF 原样建词流，行尾断词是 `addi-` + `tion` 两个 token；切块器早已把证据块修成 `addition`，模型照抄"addition"，索引里却没有这个词 | 索引按与切块器**同一套规则**接行尾断词（连字符 + 小写开头才接） |

危险之处在于它**看起来像守卫在正常工作**：界面上只有"未被支持"，没有报错。
换个数据集就全军覆没，而我们在 v7 上测的时候一条都没复现 ——
所以现在测守卫必须跨论文（v1 / v7 / BERT），单篇测不出这类"索引与切块器说法不一致"的 bug。
修复后同一问题 0/3 → **3/3 supported，全部 `exact=True`、相似度 1.00**。

### 结果

- 单测 **9/9 通过**（4 条正例防误杀，5 条反例防漏杀）
- 端到端：6 条结论 6 条通过，**每条都带页码与 bbox**
- 拦截率数字说明：本轮为 0%，因为不再截断证据后模型没再编；守卫的价值在反例测试里体现（5/5 全部拦下）

### 已知局限（面试/答辩会被问）

守卫只验证"引用是否逐字存在"，**不验证"引用是否真的支撑结论"**。
模型完全可能挂一段真实但不相干的原文。下一步需要加 claim–quote 蕴含校验（用小模型或规则做一致性打分）。

## E-003　中文提问 × 英文论文：检索词扩展值不值

**日期**：2026-10-31　**脚本**：`scripts/eval_retrieval.py`
**模块**：`app/parsing/chunker.py`、`app/retrieval/bm25.py`、`app/rag/query.py`

**问题**：用户用中文问"为什么要除以 sqrt(dk)？"，论文是英文的。
BM25 把中文切成 **0 个 token** —— 词法通道对跨语言完全失明。

**方法**：切块 → BM25 单路 vs「LLM 把问题改写成 2–3 条英文检索式 → 多路召回 → RRF 融合」。
评测集 18 题人工标注，每题对应论文中唯一正确的小节，Hit@1 不看"差不多对"。

### 结果（检索式缓存固定后）

| 配置 | Hit@1 | Hit@3 |
|---|---|---|
| BM25 单路（原始问题） | 11/18 = **61.1%** | 11/18 = 61.1% |
| 扩展 + RRF（等权） | 12/18 = **66.7%** | 17/18 = **94.4%** |
| 扩展 + RRF（首条加权 1.0/0.6/0.6） | 12/18 = 66.7% | 17/18 = 94.4% |

**关键读数不是 Hit@1，而是 Hit@3 从 61.1% → 94.4%。**
给下游 LLM 的是前 6 块而不是前 1 块，所以"正确的那块在不在前 3"比"排第一"更贴合实际收益。

### 一次被数据推翻的假设

我原以为"模型给的第一条检索式最贴题"，于是给首条加权。
第一次跑出 72.2%，加权后掉到 66.7%，看起来像加权有害。

**但那是两个不同的检索式集合。** 重新跑同样的代码又回到 66.7% ——
LLM 的扩展结果有抖动，18 题里每题错 1 道就是 5.6 个百分点，
**一次实验根本分不开 66.7% 和 72.2%**。

于是加了 `--build-cache`：先把 18 题的扩展结果落盘，再让各配置读同一份缓存。
固定检索式后，加权与等权**完全相同**（都是 66.7%）。

**教训**：凡是链路里有 LLM，评测就必须先冻结它的输出，否则测的是模型的脾气，不是你的策略。

### 单路 BM25 为什么还能有 61%

中文问题里夹着英文术语（`label smoothing`、`sqrt(dk)`、`WMT 2014`、`Pdrop`、`Adam`），
这些 ASCII 片段恰好是最有区分度的 token。纯中文的 7 道题则是 **0 召回**。
这也说明：**词法通道的强项就是精确术语**，它不该被向量通道取代，而该与之并行。

### 仍然失败的 7 道（下一轮的靶子）

| 问题 | 期望小节 | 实际第一名 | 性质 |
|---|---|---|---|
| 多头注意力用了几个头 | 3.2.2 | Attention Visualizations | 正确块在第 3 |
| 自注意力每层复杂度怎么比 | 4 | 3.4 Embeddings and Softmax | 正确块在第 3 |
| 英德翻译用哪个数据集 | 5.1 | 6.1 Machine Translation | 正确块在第 3 |
| 改变头数影响英法翻译吗 | 6.2 | 3.2.2 Multi-Head Attention | 正确块在第 3 |
| 注意力可视化能看到什么 | Attention Visualizations | 3.2.1 | 完全没进前 3 |

共性：**都是在问"概念之间的关系"，而不是在问一个能逐字命中的术语**。
`5.1 数据集` 与 `6.1 结果` 都含 `WMT 2014`，词法分不开"用哪个数据训练"和"在哪个数据上刷了多少分"——
这正是需要语义向量的地方，也是下一步做 BGE-M3 密集检索的理由。

### 顺带落地的工程约束

- 切块：28 块 / 15 页，token 52–456，段落绝不切开，标题必开新块（`tests/test_chunker.py` 9 条）。
- 检索：40 条测试全绿，含"库里没有的词宁可返回空也不能硬凑"。
- 守卫：端到端 4 条结论 → 3 条逐字命中（带页码 bbox）、1 条模糊命中（明确标注"需人工确认"）、0 条被拦。

## E-004　密集检索值不值：一次"没找到瓶颈"的诊断

**日期**：2026-10-31　**脚本**：`scripts/eval_retrieval.py --dense / --hybrid / --dense-weight`
**模块**：`app/retrieval/embeddings.py`（ONNX + tokenizers）、`app/retrieval/dense.py`、`app/retrieval/bm25.py`

**动机**：E-003 结束时剩下 5 道题，共性都是"问概念之间的关系，不是问一个能逐字命中的术语"。
按常理该上向量通道补语义。于是接了 BGE（small/en）的 ONNX 推理：
CLS 池化、L2 归一化、查询侧加 `Represent this sentence for searching relevant passages: ` 前缀，
**刻意不引 torch**（onnxruntime + tokenizers 合计不到 20MB，演示机没有显卡也跑得动）。
模型 133MB，sha256 已与上游 LFS oid 逐字节比对，Defender 全盘扫描无威胁。

### 结果（18 题，检索式缓存固定，同一份代码）

| 配置 | Hit@1 | Hit@3 |
|---|---|---|
| BM25 单路（原始中文问题，零扩展） | 11/18 = 61.1% | 11/18 = 61.1% |
| **扩展 + RRF（纯词法）** | **15/18 = 83.3%** | **18/18 = 100%** |
| 向量单路（同样走扩展 + RRF） | 12/18 = 66.7% | 16/18 = 88.9% |
| 双通道并行 + RRF 等权 | 11/18 = 61.1% | 16/18 = 88.9% |
| 双通道并行 + 向量降权 0.4 | 13/18 = 72.2% | 17/18 = 94.4% |
| 词法召回 → 向量重排（α=0.25） | 15/18 = 83.3% | 18/18 = 100% |
| 词法召回 → 向量重排（α=0.5） | 13/18 = 72.2% | 18/18 = 100% |

**没有一个向量配置超过纯词法。** 等权融合更是从 83.3% 掉到 61.1% —— 加了通道反而倒退。

### 顺着"为什么融合会变差"挖到的真问题：单复数

诊断某道失手题时，向量通道把标题为 **"Attention Visualizations"** 的那节排到了第 1，
而词法通道**整个没召回它** —— 因为查询写的是 `visualization`（单数），
`visualization` 与 `visualizations` 在 BM25 里是两个毫不相干的词。

补上 20 行的单复数归并（`-ies → -y`、`s/x/z/ch/sh + es` 整体去后缀、其余只掉一个 `s`，
且 `ss/us/is` 结尾一律不动）之后：

| 配置 | Hit@1 | Hit@3 |
|---|---|---|
| 扩展 + RRF（词法，归并前） | 12/18 = 66.7% | 17/18 = 94.4% |
| 扩展 + RRF（词法，归并后） | 15/18 = 83.3% | 18/18 = **100%** |

**十几行词形规则，拿到的比 133MB 的向量模型多。**

词干化只加在 `bm25.py`，**绝不改 `split_tokens`**：溯源校验要逐字比对原文，
把"引用原文"换成"引用近似词"等于给幻觉开后门。

### 为什么 RRF 在这里会帮倒忙

1. **票数不对等**：向量通道永远返回满 k 条，词法常常只返回 2–4 条（没命中的块根本不进榜）。
   28 块的小语料上，多一路就等于给向量那批块无条件多发选票。
2. **名次压缩**：k=60 时 rank1 与 rank6 只差 8%（1/61 vs 1/66），
   "明显第一"和"勉强上榜"在 RRF 眼里几乎等价。
3. **词法的名次本身不可靠**：短块上 BM25 全是近似平局。
   实例：`multi-head attention heads` 让 3.2 Attention(6.3297) 与 3.2.2(6.2874) 只差 **0.7%**，
   而 RRF 把这种抛硬币的结果当成了铁证。
4. **向量也没自信可按**：BGE-small 的余弦分全场挤在 0.55–0.88，
   第一名与第二名差距仅 0.004–0.134 —— 想按"向量更自信"来门控，信号不够。

### 结论（写进设计）

- **默认检索路径保持词法**：扩展 + RRF + 单复数归并，Hit@3 = 100%。
  下游 LLM 拿到的是前 6 块，所以这个指标比 Hit@1 更贴近真实收益。
- **向量模块保留、但不进默认路径**：`--dense` / `--hybrid` 是可选消融开关。
  它的价值不在当前指标，而在**下一阶段的前提**：多篇论文、跨语言（中文问 → 英文库）时词法会整体失效。
- **不在 18 题上继续调阈值**：一道题就是 5.6 个百分点，任何 ≤2 道的差异都是噪声。
  继续扫权重就是把噪声当信号 —— E-003 已经栽过一次。

### 什么情况下应该重新打开它

1. 语料从 1 篇变成 10+ 篇（词法 IDF 会被稀释，语义通道的优势才会显现）；
2. 换 `bge-large` / `bge-m3`（当前 small 版的余弦分布压得太扁）；
3. 术语稀疏的领域（人文、临床），词法拿不到精确词形当锚点。

### 顺带落地的工程约束

- `load_embedder()` 在**模型缺失、依赖缺失**两种情况下都返回 `None`，
  上层降级到纯词法而不是崩掉（`tests/test_dense.py` 用 `skipif` 保证没模型的机器也能跑测试）。
- 测试总数 40 → **61 条全绿**，新增单复数归并 12 条、向量通道 6 条、重排/平局各 1 条。
- 测试里有一条**故意只断言"进前三"**：那 0.7% 的平局是 BM25 的固有性质，
  写成"必须第一"只会让测试随机变红，然后被人删掉。

## E-005　版本谱系：v1 对 v7，把噪声和真修订分开

官方用例 3.1 要的是"传进新版，系统自己认出这是同一篇的不同版本，并说清改了什么"。
第一半（是不是同一篇）在 E-001 已经标定完；这里做的是第二半（改了什么），
以及一路上被数据推翻的三个"看起来显然"的想法。

### 基线：朴素句级 diff 不可直接使用

同一对文件（1706.03762 v1 → v7，各 15 页）：

| 做法 | 变更条数 | 可读性 |
|---|---|---|
| 逐句 `SequenceMatcher`，原样输出 | **68 块** | 60 块是"改写"，绝大多数只是脚注编号、分栏顺序、行尾连字符造成的伪差异 |
| 降噪后（本模块） | **41 条**（新增 11 / 删除 12 / 改写 18），另丢弃 **79 条**措辞微调 | 每条都带章节与页码，能直接给人看 |

关键不在"变少了"，而在**丢掉的 79 条里没有真改动**：
逐句配对用 `difflib.ratio` 分档，≥0.90 判为措辞微调丢弃，0.50–0.90 判为实质改写。
两项阈值沿用 E-001 的标定思路，用真实句子对验证过（`tests/test_versioning.py`）。

### 被数据推翻的三个想法

**① "剥掉上标脚注编号" —— 实测删了它结果一模一样**

初版 `normalize` 有一条正则，把"小写字母后跟 1–2 位数字"当脚注标记剥掉
（依据是 PyMuPDF 会把上标抽成正文："gradients 4. To counteract"）。实测在两份 PDF 上：

- 宽松版命中 **91 / 101 处**，其中真脚注不到 5 处；
  把 `BLEU 41.0` 削成 `.0`、`section 3.2` 削成 `section .2`、`Figure 2` 削成 `figure`。
- 收紧成"后接句点+空白"后仍有 **7 / 11 处**误伤（`See Figure 2. 3.3`）。
- 更要命的是：**删与不删，diff 输出完全相同**（41 条 / 79 条 trivial，一字不差）。

所以它没省下任何工作，却会让 `layer 5 of 6` 与 `layer 6 of 6` 归一化后一模一样 ——
把真改动判成噪声。已删除，并留了一条测试专门防它被"顺手"加回来。

**② arXiv 投稿戳：从"假章节"到"混进正文"**

`arXiv:1706.03762v7 [cs.CL] 2 Aug 2023` 这行戳是 20pt，**比论文标题（17.2pt）还大**。
于是切块器按字号规则把它认成一级标题，整页正文都挂到 `arXiv:1706.03762v1` 这个假章节下 ——
目录里多一条、版本对比里出现"删除 arXiv:..."这种鬼话。

而页眉页脚剔除逻辑也接不住它：那套规则只看页面上下 7.5% 的区域，
这行戳是**竖排在左边距**里的，`y` 坐标落在正文带内，重复出现也剔不掉。

修法是在切块阶段直接按内容丢弃（`ARXIV_STAMP`）。
用同一对文件验证过：剔除前后 diff 条数不变（41 / 79），
但对比结果里不再出现假章节和 `删除 arXiv:...`，
正文里真实引用预印本的（`preprint arXiv:1511.06114, 2015.`）不受影响 —— 测试两头都断言了。

**③ 标题不能从切块器的 section 里取**

v7 的版面让切块器把标题认成了 heading，于是"从 `chunks[0].section` 取标题"在 v7 上能用；
换成 v1 就认成 `Abstract`，标题直接掉回文件名 `1706.03762v1`。
BERT / GPT-3 / GPT-4 同样取不到。改成"首页字号最大的行（剔除 arXiv 戳）"后：

| 文件 | 结果 |
|---|---|
| 1706.03762v1 | Attention Is All You Need |
| 1706.03762v7 | Attention Is All You Need |
| 1810.04805_BERT | BERT: Pre-training of Deep Bidirectional Transformers for Language Understanding |
| 2005.14165_GPT-3 | Language Models are Few-Shot Learners |
| 2303.08774_GPT-4 | GPT-4 Technical Report |

**5 / 5 命中**，而旧做法只有 1 / 5。

### 结果

- 关系判定：v1 ↔ v7 = **0.7032 → `new_version`**；v7 ↔ BERT = **0.0033 → `distinct`**。
- 差异：41 条，全部标注了章节（`labeled = 41 / 41`），其中 3 条落在 References（编号位移，
  摘要前过滤掉）。
- 摘要：喂给模型的是"新旧句子对照 + 章节"，**不给结论**；返回 6 条中文，每条都挂着章节。
  实测它自己把"Google 版权声明插入"这类结构性噪声当噪声忽略了 —— 这是给提示词写清
  "忽略图表重排/编号位移/标点"的直接收益。
- 单次端到端（对齐 + 降噪 + 大模型归纳）约 **3 秒**。

### 一个必须写进答辩的诚实点

差异列表是**确定性**的（有测试断言两次结果逐字节相同）；
中文摘要在 `temperature=0.1` 下**仍会变化**，同一对文件连跑两次措辞不同。
所以：证据在 diff，摘要只是包装。摘要失败时接口返回 `summary_ok=false` +
`summary_note`（原因），前端明确显示"大模型没能归纳，下面是原始改动"，
**绝不把空摘要伪装成"没有差异"**。

### 顺带落地的工程约束

- `GET /api/papers/{id}/compare/{other}`：**新旧按 PDF 元数据里的生成日期判**，
  不按上传顺序、不按文件名。测试里故意先传 v7 再传 v1，按上传顺序会整份 diff 方向反掉。
- 测出关联度低于阈值（`related` / `distinct`）时，接口照常返回差异，
  但界面必须先警告"这两份可能根本不是同一篇的版本" —— 沉默地给出 diff 比不给更糟。
- 测试总数 61 → **107 条全绿**（新增版本谱系 23 条、对比接口 8 条）。

## E-006　引用图谱：参考文献解析 + 库内 PageRank

创新性那 25% 里，引用图谱单独占 10%。目标不是"画一张酷图"，
而是**每一根箭头都能追到参考文献里的那一行** —— 图上说"BERT 引了 Transformer"，
点开就要能看见 BERT 参考文献里的那一条。

### 参考文献解析：三种版面必须都吃下

样本里三种引用样式同时存在，靠一套正则通吃：

| 样式 | 出处 | 例子 |
|---|---|---|
| 数字标记 | Transformer、BERT | `[1] Vaswani, A., et al. ... 2017.` |
| 字母数字标记 | GPT-3 | `[VSP+17] A. Vaswani, ... 2017.` |
| 无标记（ACL 体） | GPT-4 | `Liu, X. et al. 2020. Adversarial training ... ACL.` |

每份 PDF 实际解析出的条数（**全部条目都能拆出标题和年份**）：

| 文件 | 参考文献条数 |
|---|---|
| 1706.03762 v1 | 36 |
| 1706.03762 v7 | 40 |
| 1810.04805 BERT | 54 |
| 2005.14165 GPT-3 | 144 |
| 2303.08774 GPT-4 | 85 |

v1 到 v7 从 36 条涨到 40 条，和"v7 补充了引用"这个公认事实对得上。

### 被数据推翻的四个想法

**① "附录里也有 References，一起解析没坏处" —— BERT 65 条、GPT-4 194 条**

GPT-4 的 System Card 附录自带一份参考文献，编号从 `[1]` 重新开始。
两份混在一起后，`dict` 的键直接互相覆盖，**85 条正文引用只剩下一半**，
剩下的全是附录里的垃圾条目（表格里的数字、脚注残句）。
BERT 同样从 54 涨到 65。

修法不是"过滤垃圾条目"，而是**在 References 段落遇到 Appendix / Supplementary /
Author Contributions 就停**。改完：BERT 54、GPT-4 85，且键恰好是 `1..85` 连续。

**② "句点加空格就能切条目" —— 把 Transformer 那条吞进了上一条**

ACL 体写作 `作者. 2010. 标题. 出处.`，所以条目内部本来就有句点。
初版遇到 `作者 + 年份` 的半条也认为"写完了"，于是标题另起一条，
两条引用被劈成"作者头"和"标题+出处"，Transformer 那条直接被并进上一条的 raw 里，
**在图上就是不存在的**。补齐判据（有年份 + 以句点收尾 + 有出处或正文 ≥60 字）后才正常。

**③ "年份取第一个像年份的四位数" —— 把 arXiv 号当成出版年**

`arXiv:2004.08994` 里的 `2004` 是**月份**（2020 年 4 月），它在条目里的位置比真正的
出版年更靠前。GPT-4 的参考文献里因此有一条 "Adversarial training for large neural
language models" 被标成 2004 年，而它是 2020 年。

两处一起改：先抹掉 arXiv 编号再找年份，且取**最后**一个 ——
三种版面都把年份写在条目末尾。改完后 323 条里有年份的仍占绝大多数，
少数没有年份的（`In Advances in Neural Information Processing Systems.`、
一个 blog URL）如实留空，**不拿 arXiv 号冒充**。

**④ "库内论文的年份取 PDF 生成日期" —— 图谱上写着 Attention Is All You Need (2024)**

v7 是 2024 年重新导出的，按生成日期就成 2024；BERT 的 PDF 生成于 2019，而它 2018 年发表。
改用 arXiv 号里的 `YYMM`（首次投稿年月，和引用惯例一致）：实测 4/4 全对 ——
2017 / 2018 / 2020 / 2023。取不到才退回生成日期。

### 引用匹配：标题相似度的实测间隔

先按 arXiv 号精确比，没有号才退回标题 Jaccard（去停用词、大小写、标点）。

| 配对 | 相似度 |
|---|---|
| BERT 参考文献里的 Transformer ↔ 库里的 Transformer | **1.00** |
| GPT-3 参考文献里的 BERT ↔ 库里的 BERT | **1.00** |
| **最像的假配对**：GPT-2 "Language models are unsupervised multitask learners" ↔ GPT-3 "Language Models are Few-Shot Learners" | **0.50** |

真引用全是 1.00，最好的假引用停在 0.50，中间是一段空档，
阈值取 **0.70** 两边都有余量。这条阈值有测试盯着：拿 GPT-2 那条去撞库，
必须匹配不上。

### PageRank：一度被"库外文献"整个带偏

手写幂迭代（`damping=0.85`，不用 networkx），20 次内收敛。

第一版把库内论文和库外文献放进同一张图算，理由是"文献之间的引用也该算影响力"。
实测结果：

| 节点 | PageRank |
|---|---|
| 《Outrageously large neural networks》（库外） | **0.0442** |
| 《Attention Is All You Need》（库内，被 3 篇引用） | 0.0388 |

库外文献只进不出（没有出边），在阻尼模型里变成一堆"只吸不吐"的悬挂点，
把质量全吸走了。另一种写法（把外部节点全展开成 285 个）更糟：所有排名塌到 0.0034 附近，
**差距被稀释到看不出谁重要**。

最终**只用库内论文之间的边算排名**：

| 论文 | PageRank | 被库内引用 |
|---|---|---|
| Attention Is All You Need | **0.451** | 3 |
| BERT | 0.244 | 2 |
| Language Models are Few-Shot Learners (GPT-3) | 0.171 | 1 |
| GPT-4 Technical Report | 0.133 | 0 |

与"BERT 引 Transformer，GPT-3 引这两篇，GPT-4 三篇都引"这 6 条事实完全一致。
库外文献照旧画在图上（否则图就只剩 4 个点），但 `rank` 恒为 0、不参与排名 ——
接口里这个字段有注释明说，界面上也标了"只算库内论文之间的引用"。

### 版本合并：v1 和 v7 必须是**一个**点

并查集按指纹相似度聚类（传递性：v1≈vmid、vmid≈v7 不代表 v1≈v7，所以不能两两贪心）。
代表节点取 **PDF 生成日期最新**的那一版。
不合并的后果不是"多一个点"那么轻 —— PageRank 会把被引票数劈成两半，
而"自己引自己"的边会让排名的含义整个变味。

### 布局：坐标由后端算，前端只画

确定性同心环（中心 1 → 6 → 12 → 18，半径 0.0 / 0.24 / 0.40 / 0.47，
外圈半格错位），全部归一化到 0..1 的**正方形**坐标。

- 放前端算（力导向）的话，同一份数据换个浏览器打开布局就变，
  演示时"每次打开图都不一样"最毁信任。有测试断言两次调用坐标逐位相同。
- 一开始按 viewBox 的宽高分别乘，环被压成椭圆，标签全挤在一起；
  改成正方形映射后才是圆的。

### 顺带落地的工程约束

- `GET /api/graph?max_external=N`：N 被夹到 `0..60`。前端传 9999 不该 500，也不该真塞一千个点。

大赛文档要求验证大文档鲁棒性，库里放一本 541 页的《Understanding Deep Learning》。
它和前面四篇论文**没有一个结构特征相同**，于是把切块与参考文献解析的隐含假设逐个打穿：

| 现象 | 原因 | 改法 | 数字 |

| 953 块里九成章节名是公式碎片 | 显示公式以数字开头（`0 + ϕ′ 1a [ψ10 + …`），命中"编号 + 空格 + 内容" | 编号后那截要**像标题**：首字符是字母、字母占比 ≥ 0.45 | 章节名恢复可读 |

## E-007　"点了没反应"：一个属性赋值，废掉全站一半的点击

用户报的三件事看着毫不相干：

1. 阅读器永远只有第一篇论文；
2. 点目录里的标题会**跳回**文献库；
3. 版本谱系点「对比差异」没反应。

查下来是**同一个根因**：所有动态生成的节点都走同一个 `el(tag, { on: {...} })` 辅助函数，
而它把事件写成了 `Object.assign(node, { click: fn })` —— 那是**给 DOM 的 `click` 方法赋值**，
不是注册监听器。真实鼠标点击派发的是事件，永远不会调用被覆盖掉的那个属性。
于是文献库整行、目录每一条、引用的「跳转到原文」、差异条目的「→」、图谱的「打开全文」
**全都点不动**，而代码读起来完全正常。

第二个症状是它的连锁反应：目录条目是 `<a href="#">`，本该在监听器里 `preventDefault()`；
监听器从没执行 → 浏览器照常跳到空 hash → `hashchange` 把视图打回 `library`。
用户看到的就是"点标题自动跳回文献库"。

修法一行：`for (const [ev, fn] of Object.entries(v)) node.addEventListener(ev, fn)`。

第三个症状另有其因：版本下拉的默认值是**全库**最早 + 最晚，库里放进 541 页教材后，
默认对就是「Transformer v1 → 教材」，逐句对齐根本跑不完，按钮像坏了。
改成按归一化标题分组，优先取同一篇的最早 / 最晚两版（教材没有第二版就不参与默认对）。

| 修前 | 修后 |
|---|---|
| 点文献库任意一行：视图不变，正文不变 | 切到阅读器，载入该篇，标题/页码立刻更新 |
| 点目录：`view-reader` → `view-library` | 停在阅读器，`#page-title` 从 `Abstract` → `3 BERT` |
| 版本默认对：Transformer v1 vs 541 页教材，状态永远停在「逐句对齐中…」 | 默认 Transformer v1 vs v7，**5.0 s** 出 41 处改动 |
| 差异条目「→」、图谱「打开全文」无反应 | 分别跳到 `p.2` / 对应论文正文 |

### 顺带补的两处"只有一个人能用的界面"

- 阅读器**没有换文献的入口**：`loadPapers()` 自动打开 `papers[0]` 之后，就没有第二条路径进别的论文。
  加了「当前文献」下拉，库变了自动重填。
- 文献库点行只调用 `openPaper(id)`，不切视图 —— 数据换了、页没换，看着就是"没反应"。
  改成 `openInReader(id)`：先切视图再载入。

### 点击回归测试

用 CDP 逐个点过 18 个交互点（6 个视图切换、主题、搜索、表头排序、刷新、整行点击、
换文献下拉、目录、原始 PDF 链接、问答 + 引用回跳、版本对比、差异跳转、图谱节点、
影响力条、打开全文、中英对照翻译 + 段落切换 + 导出、Copilot 生成 + 编号定位、
CSV 图表 + 导出）。修完后全部通过；顺带抓到两个新 bug：

- `replaceChildren(…, cond ? el(…) : null)` 会把 `null` **渲染成文字 "null"**（`el()` 会跳过 null，
  原生 `replaceChildren` 不会），译文栏底部凭空多出一行 "null"。
- 降级有两种（模型挂了 / 段数对不上），早先按 `degraded` 一刀切显示"只有原文"，
  把已经翻好的段落也丢掉了。改成看"有没有任何一段译文"。

## E-008　两个"设计稿示例"变成真功能

中英对照和写作 Copilot 之前只是静态设计稿（卡片上挂着「设计稿示例」的标签）。
补成真功能时的取舍都围绕同一条原则：**大模型只负责措辞，不负责事实**。

### 中英对照：段落数是硬契约

| 决定 | 理由 | 数字 |
|---|---|---|
| 按空行切段，一次翻完整个块 | 段落是天然的对照单位；一句一句调会丢上下文、成本还更高 | Transformer 3.2.1 块 10 段，**2.2 s** |
| 段数不符就降级，不硬凑 | 模型爱把两段合成一段或把公式单独拆行；硬凑出来的并排显示必然错位 | 不符时标 `degraded=true`，已对齐的部分照常显示 |
| 模型挂了返回 **200** | 断网演示还得继续：原文永远在本地，译文只是增强项 | 失败分支不写缓存，恢复后可重试 |
| 成功结果按 `(paper_id, chunk_index)` 缓存 | 同一段反复看不该反复扣费 | 二次请求 0 次模型调用 |
| 导出的 Markdown 逐段成对 | 对照稿离开页面就成了两段互不相干的文字 | — |

### 写作 Copilot：编号由服务端发，引用由服务端填

模型只准返回**证据块编号**，`quote` 一律由服务端从块正文里截取（≤200 字）。
不在本轮证据里的编号直接丢弃，要点退化成 `evidence: []` 并在界面上标成「待补证据」——
这正是评委最容易追问的点：*你怎么保证框架里的引用不是编的？*

- 检索跨全库（不只是当前这篇），先做检索词扩展再逐篇 BM25，全局排序取前 8 条。
- 0 召回时（通常是断网导致扩词失败）退回每篇首块作**演示兜底**，并在注释里写明这不是检索结果。
- 实测一次：6 章节 / 21 条要点 / 6 条真实引用，**5.8 s**；每条引用都能点回原页。
- 降级（模型挂了）：`outline` 为空但 `references` 照常返回 —— 至少能告诉用户"库里能引用哪些原文"。
- 输入框给的是**占位提示**（`示例：…`），不是填好的 `value`。填死的值会让人以为
  "已经生成过什么"，甚至照着别人的题目往下改；而占位提示一输入就消失。但框空着点「生成框架」
  仍按那个例子跑 —— 评委点一下要看到东西。代价是必须**说出来**：这行字被填回框里，
  状态栏标「用的是示例 idea」，否则框架看着像是根据他自己写的东西生成的，那是另一种编。

### 数据可视化：CSV 不出这台机器

前端本地用 `FileReader` 解析、本地画 SVG，**不走网络** —— 实验数据往往是还没发表的。
图注只写图里能量出来的事实（最高 / 最低 / 相差百分比），不写"表明""证明"这类因果断言，
并明说"不含误差棒，差异是否显著需另做检验"。轴上限取 1/2/5×10^k，网格线落在整数上。

测试 158 → **171 条全绿**（新增中英对照 7 条、Copilot 6 条，全部用 monkeypatch 换掉模型调用）。

## E-009 删除：一处不删就等于没删

「文献库只能上传不能删除」是最先被用出来的一句话 —— 评委传错了文件，只能重启服务。
补这个接口时真正的问题不在 HTTP 层，而在**同一篇文献同时存在三个地方**：
内存里的 `_papers`、落盘的 `<id>.json` sidecar、落盘的 `<id>.pdf`。

| 只删了哪里 | 现象 |
|---|---|
| 只删内存 | 重启后 sidecar 把它复活 |
| 只删 sidecar | `_load_existing` 的裸 PDF 扫描那一步照样把它捞回来 |
| 只删 PDF | 内存里还在，列表里还看得见，点进去必 500 |

所以"删干净"的判据写死成 store_dir 里既无 `<id>.pdf` 也无 `<id>.json`，
并加了一条测试专门重启一次注册表再断言它**没回来**。

另外两处细节是踩出来的，不是设计出来的：

- 只删 `paper.path.parent == store_dir` 的副本。万一将来有人把原始文件路径塞进
  `Paper.path`，这个接口不该连坐删掉用户的原件。
- 界面上是两步（`删除` → `确认删除`，4 秒后自动复位），而不是原生 `confirm()`：
  `--js` 驱动的验证脚本点得到普通的按钮，点不了浏览器的模态框，而且模态框会阻塞整页。

CDP 实测一次完整删除：行点击后 `#paper-pick` 指向 `4c59cb24ad29`、`4 页 · 7 块`；
点两次删除后表格 8 → 7 行、该行消失、`state.paper` 回到 `null`、阅读器清空。

### 顺带查清了「上传的文档能不能识别目录」

能，而且是**上传那一刻现算的**，不是预先做好的索引：
`registry.add()` 里调 `chunk_pdf()`，标题识别走字号第一（`2 Method`）、
层级靠编号（`2.1` 在 `2` 下面，显示成 `2 Method › 2.1 Sparse Windows`）。

拿一份 4 页的合成 PDF 实测，抽出的目录是：

```
0 p.1  132 tok | Abstract
1 p.2  132 tok | 1 Introduction
2 p.2   71 tok | 2 Method
3 p.3  132 tok | 2 Method › 2.1 Sparse Windows
4 p.3   71 tok | 3 Experiments
5 p.4   71 tok | 3 Experiments › 3.1 Setup
6 p.4   71 tok | 4 Conclusion
```

541 页教材是 406 条（首条是标题，末条是 Index）。**边界情况**也是这次试出来的：
第一版合成 PDF 里我把同一段正文重复了三遍来填页面，结果整段正文被当成页眉页脚剔掉了
（"同样的文字在页面上反复出现"正是 running header 的特征），最后只剩标题，
块数 1、章节名错成 `4 Conclusion`。真论文不会逐字重复整段，但这个坑值得写下来：
**判断依据是版面重复性，不是内容重要性**。

## E-010　综述的"证据"里有 29% 是参考文献表

综述模块一开始只做了一件事：对每篇论文检索一次，把分数最高的六块当证据喂给模型。
写完之后抽查引用栏，发现有些引用长这样：

> [1] RWC+19, KMH+20, MKAT18, ... Radford, Wu, Child, Luan, Amodei, Sutskever. Language models are unsupervised multitask learners. OpenAI blog, 2019.

这不是论文的观点，是论文的**参考文献列表**。它被当成"证据"引用了。

### 量一下到底有多少

五篇论文（Attention Is All You Need 的 v1 与 v7 各算一篇）× 四条通用检索式 × 每篇前 6 块：

| 指标 | 数值 |
|---|---|
| 原始召回 | 112 条 |
| 其中参考文献表 / 章末索引 | **33 条（29%）** |
| 单条被命中的参考文献块长度 | 1814–2644 字符 |
| 最严重的一篇 | GPT-4 Technical Report：`attention mechanism` 与 `few-shot learning` 各 4/6 条 |
| 0 召回时旧兜底取的"每篇首块" | 5 篇里 **2 篇**是作者名/邮箱/版权声明 |

参考文献块为什么分数高：它在一页里密集出现所有领域关键词，
BM25 的词频项自然吃满；而它又长（2000+ 字符），切块器把它切成一整块，
于是"一节=一整页参考文献"，检索到一次就污染一大段上下文。

### 改法：从"分数最高的块"到"能当证据的块"

1. **参考文献表直接排除**：`section` 命中 `references|bibliography|参考文献` 的块，
   或者正文里 `[n]` 形式的数字标记出现 6 次以上的块，一律不进证据、不进 Future Work。
   两个判据都要，因为有的 PDF 把参考文献表放在名为 `References` 的一节里，
   有的（ACL 版面）藏在正文最后一页且不带标题。
2. **0 召回不再退回"首块"**：改成取第一个既不是前置内容（标题页、版权、作者单位）
   也不是参考文献表的块。旧的兜底会把整篇综述的引用都变成第 1 页的作者名单。
3. **多条检索式合并去重**：中文主题查英文库时单条检索式基本 0 召回（E-003 量过），
   改成扩展出多条检索式、每篇各查一次、按块去重取最高分，再统一排序。
   单条检索式报错（索引坏了、空串）只丢那一条，不影响整批。

改完之后同一个问题（GPT-3 "有多少参数"）的引用变成了正文：

> "To study the dependence of ML performance on model size, we train 8 different sizes of model,
> ranging over three orders of magnitude from 125 million parameters to 175 billion parameters…"

## E-011　两处"少做一步就丢用户数据"的坑

这两条都不是设计出来的，是被现场打脸打出来的。共同点：**报错不明显，
损失却是真的** —— 一次手滑重传、一次删除，用户的东西就没了。

### 1. 同文件重传 + "保留库里那版"，删掉的是原件

去重策略里 `keep` 的语义是"库里那版不动，把刚传进来的这份撤掉"。
实现时照字面写成了 `registry.remove(新上传.id)`，看上去天衣无缝。

问题出在 `registry.add()` 里：**内容哈希相同就直接返回库里那个对象**
（这是"同一份 PDF 传两次落同一个 id"的前提，版本谱系靠它工作）。
于是重传同一个文件时，"新上传的这条"其实就是**用户在库里的那条**，
`remove` 删掉的是唯一的一份原件。演示时只要有人手滑一次重传，文献库少一篇。

修法是把"这份字节已经在库里"和"这是一篇新版本"分开：
`PaperRegistry.lookup(data)` 先按内容哈希问一句，命中就直接返回库里那篇，
不再走任何删除分支。测试 `test_reuploading_identical_bytes_never_deletes_the_stored_copy`
锁的是这条 —— 它断言的不是响应码，而是**库里那篇还在**。

### 2. Windows 上删文件会偶发失败，而失败之后它会自己回来

`DELETE /api/papers/{id}` 在现场 500 了，日志是 `PermissionError: [WinError 32]`：
"另一个程序正在使用此文件"。占着它的不是我们自己的代码（`TextIndex` 读完就 close），
是**刚落地几秒的 PDF 被系统的杀毒/索引服务短暂持有**。

更难看的是失败之后的状态：内存里已经从库里摘掉了，磁盘上的 PDF 还在。
下次启动 `_load_existing` 的裸 PDF 扫描又把它捞回来 —— 用户看到的是"删了又回来"。

三件事一起做才干净：

| 做法 | 原因 |
|---|---|
| 删除重试 6 次、退避 0.12s×(i+1) | 这类占用只持续几十到几百毫秒，重试比立刻放弃有效 |
| 重试全失败就**把内存里的删除撤销** | 宁可整个操作失败、库里状态一致，也不要留下幽灵文件 |
| 对外报 409 + 人话 | "这份 PDF 正被别的程序占用" 是可操作的信息，500 不是 |

两条测试分别锁"重试能救回来"和"重试失败必须回滚"（后者用一个一直占着句柄的
假文件模拟）。顺手清掉了一次现场留下的孤儿文件 `<id>.pdf` 与 `<id>.json`。

### 顺带：页面分两段脚本，变量不共享

前端是单文件，但 `<script>` 有两段：第一段管视图路由与主题，第二段是全部业务。
给主题按钮加"切深色后请后端重画图表"时想当然直接调了第二段的函数，
结果深色主题下图表一直在转圈。原因很朴素：**两段脚本各有各的作用域**，
第二段的 `VIZ`、`fetchServerChart` 在第一段里根本不存在，抛 `ReferenceError`
后异常被 async 函数吞掉，只剩状态栏挂着"服务端统计中…"。

修法是第二段往 `window` 上挂一个 `__onThemeChange` 钩子，第一段只负责喊一声。
写在这里是因为这个坑没有报错、没有日志，只有"看起来在加载"——
和 E-007 的"点了没反应"是同一类问题：**没有异常的失败最难查**。

## E-012　导航栏三个 tab"点了没反应"，外加两个 tab 看着比别的大

用户连着报了两条：**文献检索 / 学术综述「一开始点击没反应」**，以及这两个 tab
**看着比别的大**；追问一句又补上**任务 Agent 也一样**。

### 先量，别猜

CDP 在 1440 / 1100 / 1024 / 900 / 760 五个宽度下把 9 个 tab 的盒子全量了一遍：

| 标签 | 宽度 | 字号 / 高 / 内边距 |
|---|---|---|
| 文献库、阅读器 | 63 | 13px / 34 / 7px 12px |
| 版本谱系、中英对照、引用图谱、**文献检索**、**学术综述** | 76 | 同上 |
| 任务 Agent | 92 | 同上 |
| 写作 Copilot | 99 | 同上 |

字号、行高、内边距、高度**完全一致**，宽度差异只来自标签字数 —— 所以"大"不是样式错乱，
是**宽度不齐**：四字的「文献检索」「学术综述」比左边三字的「文献库」「阅读器」宽 13px。
一排 tab 里混着 63 和 76，看上去就是"有几个特别大"。

### 点击：加载器挂在了永远不会发生的事件上

视图切换走 `activate()`，它用 `history.replaceState` 改 hash —— **replaceState 不触发
`hashchange`**。而按需加载的四个视图（图谱 / 版本 / 中英对照 / 任务 Agent）里，
三个把 DOM 监听的 `hashchange` 当作唯一入口，只有图谱额外挂了一条 `nav` 的 click。

后果最明显的是任务 Agent：`loadAgentTools()` 只挂在 `hashchange` 上，点导航栏进去
它一次都不跑，右栏永远停在初始化那句话「正在读取工具清单…」—— 页面切了，
但看起来什么都没发生。文献检索 / 学术综述没有按需加载，切视图本身是成功的，
但缺了"进来就能打字"的落点，光标还在原地，感受上和没反应一样。

修法是**把"进视图要做什么"收成一个入口**：

```
activate(name)  →  window.__enterView(name)      // 第一段脚本只负责喊一声
enterView(name) →  graph / version / compare / agent 各自加载，检索 / 综述聚焦输入框
```

原本散在第二段脚本里的 6 条 `nav` click + `hashchange` 监听一并删掉 —— 它们和
`activate()` 会重复触发（图谱要请求两次、`ensureCompare` 要重填两次）。

### 宽度：够宽才撑齐

`@media (min-width:1060px){ nav button{min-width:76px} }`：四字标签的宽度成为下限，
三字的补到同一宽。窄于 1060 不撑 —— 撑了就得横向滚动，反而看不全；
这时 `nav` 常驻 `overflow-x:auto`，宁可滑一下也不把 tab 挤到右边的主题按钮上
（1024 下量过，`nav` 右边缘距主题按钮还有 48px，不重叠）。

### 用真鼠标点一遍

`element.click()` 绕过了命中测试，有东西压在上面它照样触发 —— 所以验证用
`Input.dispatchMouseEvent` 发真实的按下 / 抬起，再看视图里到底有没有东西：

| 点击 | 修前 | 修后 |
|---|---|---|
| 任务 Agent | `#view-agent` 切换成功，右栏停在「正在读取工具清单…」，`.tool` 计数 0 | 9 个工具卡片渲染出来 |
| 引用图谱 | 28 个节点 —— 它本来就能用，因为额外挂了一条 nav click | 28 个节点（改走统一入口） |
| 文献检索 | 视图切换，无落点 | `document.activeElement` = `#arx-q` |
| 学术综述 | 视图切换，无落点 | `document.activeElement` = `#rv-topic` |

回归：深链 `/#agent` 直接进（9 个工具）、`location.hash` 手改（`#graph` → 28 节点）、
`history.back()` 后退回图谱，三条路径都正常；9 个视图逐个切过去，`window.onerror`
抓到 0 条。

## E-013　arXiv 下载：TLS 1.3 慢 6 倍，断流还不报错

用户报的是两句话：「**入库失败：下载 arXiv PDF 失败：The read operation timed out**」
和「**无法下载入库**」。看着像一个网络问题，量下来是三个叠在一起的问题。

### 一、先排除"本机网络慢"

同一个 `urllib`、同一台机器，换一个主机：

| 目标 | 结果 |
|---|---|
| `pypi.tuna.tsinghua.edu.cn` 索引页（848KB） | 0.4 s，约 **2 MB/s** |
| `arxiv.org/pdf/1706.03762` 前 512KB | 31.7 s，约 **16 KB/s** |

问题只出在 arXiv 这一条链路上。

### 二、TLS 版本是关键变量

同样的请求，只改 `ssl` 的最高版本：

| 条件 | 512KB 用时 | 速度 |
|---|---|---|
| 默认（协商到 TLS 1.3） | 31.7 s | 16 KB/s |
| 最高版本锁 TLS 1.2 | 5.4 s | **95 KB/s** |
| 锁 1.2，下载全量 2.1MB | 10.5 s | 207 KB/s |

arXiv 在 Fastly 后面，本机 Python(OpenSSL) 与它协商 TLS 1.3 时吞吐掉到六分之一。
这不是"1.2 更兼容"，是 1.2 更快。

> 后续：这条结论只对**下载**成立。把 1.2 当成全局默认之后，`export.arxiv.org`
> 的检索直接握手超时，推荐页整页空白 —— 见 E-016 的反向实测与最终方案
> （按主机试一次、记住哪种走得通）。

### 三、锁了 1.2 还是会失败：三分之一概率卡到超时

同一份文件连跑两次：一次 10.5 s 拿到，一次卡到 118.9 s socket 超时。
`export.arxiv.org`（Atom 接口）也一样时好时坏。结论是**必须重试**：
下载连试 3 次、每次退避 1s/2s、每次 60 秒超时；检索不重试（只有 8KB，
失败已经降级成 200，不该让用户等三倍时间）。

### 四、最阴的一条：断流时 `read()` 不抛异常

重试加上之后，下载"成功"了，PyMuPDF 却报：

```
PDF 解析失败：Failed to open file '…/747062a83c36.pdf' as type pdf.
```

去看落盘的文件：**815,357 字节**，而完整文件是 **2,215,244 字节** ——
尾部停在一个 `/Resources << /ExtGState << /GS0` 中间。也就是说连接被对端
正常关闭，`response.read()` 拿到的就是半截，**没有任何异常**，
连 `Content-Length` 都不看就交给了解析器。

两条判据同时用上：

| 判据 | 拦住什么 |
|---|---|
| `Content-Length` 与实际字节数不符 | 声明了长度却断流（最常见的那次就是它） |
| 结尾 2KB 内必须有 `%%EOF` | 没声明长度、靠 close 分帧的响应也能认出来 |

不合格就当这次下载失败、进入下一次重试 —— 重试的是**下载**，不是解析。
不含 `%PDF` 头的响应（HTML 限流页）不重试：那不是"没下完"，是内容不对，
该按 400 报给用户。

### 修完实测

```
POST /api/tools/arxiv/ingest {"arxiv_id":"1706.03762"}
→ 201  fetched_bytes=2215244（与完整文件一字节不差）
        title="Attention Is All You Need"  pages=15  chunks=28
        duplicate_of=0a9bff1be357  relation=new_version
```

用时 60.6 s（含两次重试）。测试锁住四个新分支：一次超时后第二次成功、
三次全超时且错误里写明次数与绕行办法、半截 PDF 触发重下、非 PDF 只请求一次。

## E-014 · 多来源文献检索：五个站谁真能用

**起因**：用户搜《Attention Is All You Need》在 arXiv 搜不到（拼成 "your need"
是一半原因，另一半见 E-013 的握手超时）。修好 arXiv 之后，问题变成更根本的一条：
**只查 arXiv 就只看得见预印本**。NeurIPS / CVPR / 期刊版、数据集、论文配套材料
都不在 arXiv 上。

动手之前先把候选站各打一枪，记录"通不通、多快、给不给 PDF"：

| 站点 | 结果 | 耗时 | 给到的关键字段 |
|---|---|---|---|
| OpenAlex | `200`，72 KB | 3.1 s | `best_oa_location.pdf_url`（含 `arxiv.org/pdf/1706.03762`）、DOI、年份、机构 |
| Crossref | `200` | 1.5 s | DOI、期刊名、年份；**没有 PDF 链接**，相关性偏弱 |
| Semantic Scholar | `429` | 1.8 s | 需要 API key，不配就一路限流 |
| Zenodo | `200`，26 KB | 15 s（首次） | `files[].links.self` 直链 PDF、`metadata.description` 是 HTML |
| DBLP | `000`（连不上） | 10.6 s 超时 | — 放弃 |

结论：**OpenAlex 是性价比最高的一站**（覆盖面最广又给 OA PDF），Crossref 补正式
发表版本，Zenodo 补数据集与配套材料，S2 留接口但默认降级。DBLP 不可达，直接不写。

### 三个设计决定

1. **并发 + 各自降级 + 总时限**。五个站同时发，每站的失败只影响它自己那一栏。
   再加一个 `DEADLINE_SECONDS = 20`：超过时限没回来的站记成「超时」，
   其余结果照发。不加这条，最坏情况是所有站超时叠加（15 s 检索 × 2 次重试），
   界面上就是一大段看不出在干什么的空白。
2. **去重认"全部身份"，不认"一个 key"**。一篇论文在四个站上的标识各不相同：
   OpenAlex 给 `arxiv:1706.03762`，Crossref 只给 `doi:10.48550/arxiv.1706.03762`，
   再来一个抹平标点与大小写的标题 key。三者取交集为空也算同一篇 ——
   只用一个 key，同一篇文章会在列表里出现两遍。
3. **能不能入库要说真话**。本项目的入库通道就是 arXiv：只有解得出 arXiv id 的
   条目才给「入库」按钮，其余给「原文」与「PDF」链接。给一个点了必然 400 的按钮，
   比不给更糟。

### 界面：先写成开关，被用户当场否掉

第一版把来源做成"默认全开、点一下关掉"的开关。真实反馈是反的：

> 点击是选择不是关闭 · 还能多选网站 · 再点一次全部就取消全部

用户点 arXiv 的本意是"查 arXiv"，结果那一栏反而被关掉了。改成：

- 默认「全部」高亮 = 五个站都查，**所有站名一起高亮**；
- 全选状态下点某个站 = 收窄成"只查它"；
- 之后再点别的站 = **追加**，几个站一起亮就是一起查；
- 「全部」再按一次 = 全不选（此时点「检索」只提示不会发请求）；
- 点按钮不再往状态行写字（高亮本身就是反馈），说明文字也从卡片里删掉。

### 实测

```
GET /api/tools/search?q=attention is all you need
→ 200  38 条（去重后）
  OpenAlex   25 条 / 9.9 s
  Crossref   25 条 / 4.8 s
  arXiv      超时（20 s 时限）
  S2         429
  Zenodo     SSL UNEXPECTED_EOF
  → 卡片首条 "Attention Is All You Need" · arXiv:1706.03762 · 带「入库」
```

```
GET /api/tools/search?q=…&sources=arxiv,openalex,crossref
→ 全部成功；同一篇论文只出现一次（arXiv 那条胜出，Crossref 的 NeurIPS 版本被并入）
```

测试 18 项覆盖：五个身份写法解析、跨站去重、单站挂掉不影响其余、429 折叠成
一句 note、Zenodo 的 HTML 描述转纯文本、超时站不拖住整次检索、端点在全网断开时
仍返回 200。全套 **323 项通过**。

## E-015 · arXiv 动态追踪与本地相关推荐

**要做的事**（赛题模块四后半段）：定期刷新 arXiv 最新论文 → 结合本地库算相关性 →
优先推带开源代码的 → 给推荐理由 → 支持点赞/踩。

### 相关性别交给向量模型

本机有 BGE 的 ONNX 实现，但这里没用它，两个理由：

1. **模型可能不在**（`models/` 目录是可选依赖），推荐页不能因此整页降级；
2. **理由要能被用户看懂**。"相似度 0.83" 没人能验证，"与《Attention Is All You Need》
   词面重合 0.31" 是可以点开那篇论文自己看的。

实现是二元向量余弦：`|A∩B| / sqrt(|A|·|B|)`，A 是候选论文标题+摘要的关键词集合，
B 是库里某篇论文标题+前两块的集合。前两块而不是全文 —— 摘要和引言已经交代了
问题与做法，实验细节会把关键词表撑大，余弦反而被稀释。

### 推荐理由由模板拼，不交给大模型

理由是"为什么推给你"的证据。交给模型自由发挥，就会写出"提出了全新架构"这种
原文里没有的断言 —— 这正是赛题最忌讳的。这里每条理由都能追到具体数字：
重合哪几篇、重合多少、代码地址原文是什么、几天前提交。日期解析失败就**不写**
新鲜度那一条，绝不编一句"刚刚提交"。

### 开源代码在 `<arxiv:comment>` 里，不在摘要里

作者常把代码地址写在 arXiv 的 comment 字段（"Code: github.com/…"），摘要里反而没有。
原来 `parse_atom` 没解析这个字段，补上之后覆盖率明显不同。只认 `github.com/owner/repo`
一种形态 —— 把任意链接当仓库，用户点进去看到一篇博客，比不给链接更糟。

### 打分

```
score = 0.75 × min(1, 相关性/0.5) + 0.20 × 有代码 + 0.05 × 新鲜度
```

权重手调，不是学出来的。相关性用 0.5 做归一化上限（实测词面余弦很少超过 0.5，
超过基本就是同一篇的不同版本），所以它仍是决定性的一项；代码与新鲜度只用来在
同一条水平线上分先后 —— 正好对应赛题"优先推荐易复现的"。

### 被 arXiv 上了一课：3 秒一次是硬要求

调试期间反复请求 `export.arxiv.org`，随后拿到：

```
HTTP 429  14 bytes  52.2 s
Rate exceeded.
```

注意这个 **52 秒**：对方不是立刻回 429，而是先把连接按住近一分钟才回。于是
urllib 在 15 秒处超时，我们看到的错误是 `The read operation timed out`，
**完全看不出是被限流了** —— 排查方向会跑偏到"网络不稳定"。

两条修正：

| 修正 | 原因 |
|---|---|
| 同一主机强制 3 秒间隔（`net._throttle`，按主机加锁排队） | arXiv 使用条款的明文要求；不同主机各排各的，多来源检索照常并行 |
| 刷新失败退回上次成功的那批，并写明"N 分钟前刷到" | 限流期间整页空白是最差的体验；推荐页给的是候选，不需要秒级实时 |

（"追踪不重试"这条当天就被 E-016 推翻了一半：失败的形态变了，
真正的重试规则落在网络层。）

### 实测

```
GET /api/recommend?categories=cs.CL,cs.LG&days=7&limit=6
→ 200  6 条 · 比对库里 6 篇 · 每条都带 reason
GET /api/recommend（15 分钟内再来一次）
→ cached=true，不出网（实测 7 毫秒返回）
arXiv 拿不到时
→ 200 + degraded=true + note「arXiv 追踪失败：…；下面是 N 分钟前刷到的那批」
```

测试 16 项覆盖：词面相关性、理由里的数字、`comment` 里的代码地址、空库仍能推荐、
日期缺失不编新鲜度、投票的改票与取消、落盘原子性、失败回退旧批次。
（当时的 339 项，之后加 `test_net.py` 13 项，全套 352 项。）

## E-016 · 推荐页整页空白：不是 arXiv 挂了，是我们的 HTTPS 客户端

E-015 上线后 `/api/recommend` 一直降级，`note` 里是这两句之一：

```
arXiv 追踪失败：<urlopen error _ssl.c:993: The handshake operation timed out>
arXiv 追踪失败：<urlopen error [SSL: UNEXPECTED_EOF_WHILE_READING] EOF occurred ...>
```

同一时刻用 curl 打**同一条 URL**，200、0.3 秒、32KB 全拿到。所以既不是
arXiv 挂了，也不是 IP 被封 —— 是我们自己的客户端在这条路径上有问题。

### 一层层剥

| 怀疑对象 | 怎么验 | 结论 |
|---|---|---|
| IP 被限流 | curl 立刻 200 | 不是（真限流时 curl 也会 429） |
| UA 被针对 | curl 带上项目 UA、强制 HTTP/1.1 | 不是，0.38 秒 |
| IPv6 路由坏 | `curl -6` 0 毫秒失败、`getaddrinfo` 只有 IPv4 | 不是 |
| 系统代理 | `urllib.request.getproxies()` → `127.0.0.1:7897` | **是主因之一** |
| TLS 版本 | 同一条 URL 强制 1.2 / 放行 1.3 各打几次 | **是主因之一** |

### 数据

同一条 32KB Atom feed，四组跑法：

| 跑法 | 结果 |
|---|---|
| curl 直连 | 200，0.3~1.6 秒 |
| curl 直连 + `--tls-max 1.2` | **30 秒超时，0 字节** |
| curl 走代理（默认协议） | 200，3.1 秒 |
| curl 走代理 + TLS 1.2 | 30 秒只收到 15081/32725 字节 |
| Python 直连 TLS 1.3 | 3/5 成功，成功时 1.7~4.9 秒 |
| Python 走系统代理 TLS 1.3 | 2/3 成功，1.1~5.1 秒 |
| Python 任意路径打 pypi.org | 52 秒读超时 |

两件事定了：

1. **TLS 1.2 在这条网络上基本废了**（curl 直连都 30 秒零字节）——
   E-013 里"锁 1.2 快六倍"的结论换了网络环境就反转了，所以不能写死。
2. **系统代理是全局的**：urllib 默认读注册表，所有请求都多绕一跳；
   curl 不读注册表，所以一直快。

### 改法（写进 `net.py`，四件事）

| 改动 | 为什么 |
|---|---|
| 默认直连，`RESEARCH_PROXY=system` 可改回 | 注册表那个代理让每次请求多绕一跳，还更容易整段超时 |
| 先默认协议（1.3），连接建不起来才换 1.2 重发一次，胜出的按主机记住 | 两个版本各有各的坏法，写死哪个都会翻车 |
| 只在"请求还没发出去"时重试（`ConnectFailed`） | 握手失败重发是对的；读超时多半是被按住了，重发是往封禁窗口里再扔一个请求 |
| 请求默认带 `Accept-Encoding: gzip` | 32KB 的 feed 压缩后只走几分之一，而这台机器上就是缺带宽 |

顺带两处配套：追踪只抓 `limit*2`（48 条 = 120KB，多抓的每一千字节都是白等的一秒）；
失败退回旧批次已经在 E-015 做过了，这次它第一次真的救场。

### 实测

```
GET /api/recommend?categories=cs.CL,cs.LG,cs.AI,cs.CV&days=7&limit=12
→ 200  12 篇 · 比对库里 6 篇 · 每条都带 GitHub 地址
   例：「与库里的《GPT-4 Technical Report》词面重合 0.16；另外还命中 2 篇；
        摘要或备注里给了开源代码 https://github.com/…；3 天前提交」
GET 同一条（15 分钟内）→ cached=true，7 毫秒
POST /api/recommend/vote  {"arxiv_id":"2610.40616","vote":"up"}  → 票数 1
POST 再来一次 vote:""                                          → 票数 0（取消）
```

首次冷启动仍可能要 20 秒左右（要换手重发一次），所以界面上有骨架屏
和"正在刷新 arXiv 最新提交…"这行字 —— 慢的时候看得见在做事。

新增 `tests/test_net.py` 13 项：换协议重试、记住胜出的协议、读超时不重试、
5xx 不重试、半截内容不重试、`attempts=1` 只打一次、`ARXIV_TLS13` 只走默认协议、
默认绕开系统代理、`RESEARCH_PROXY` 两种取值、gzip 解压、长度不足要报错。
全套 **352 项通过**。

## E-017 · 一轮"自己点着玩"测出来的三个 bug

按用户要求（"继续完善，你可以测一下 bug"）把每个接口都真打了一遍，
专挑演示时会被点到的路径。三个问题，一个比一个藏得深。

### 一、把一本书和一篇论文放一起对比，接口跑了两分钟

`GET /api/papers/f79d7cf30bb4/compare/f8237d393163`（一篇 6 页论文 vs 一本 550 页的书）
—— **60 秒超时**，去掉大模型摘要（`summarize=false`）再打，**120 秒还是超时**。
跟模型没关系，是 diff 本身：

```
load_sentences(论文)  0.12 s   348 句
load_sentences(书)    9.51 s  11247 句
SequenceMatcher 给出的 opcode：3 个，其中一个是 replace  342 × 10737
```

两边的正文几乎没关系，`difflib` 于是吐出一个"整块替换"，而 `_refine` 会在块内
做**逐句两两配对**：342 × 10737 = **367 万次** `SequenceMatcher.ratio()`。
作者在 docstring 里写的假设是"块内句数通常 < 50，平方复杂度无所谓" ——
这个假设只在"同一篇论文的两个版本"里成立。

改了两处（`app/versioning.py`）：

| 改动 | 效果 |
|---|---|
| 先比长度：`ratio = 2M/T ≤ 2·min(la,lb)/(la+lb)`，上界够不到 `MATCH_RATIO` 的句对直接跳过 | 长度差三倍以上的句对连字都不用比；这是严格上界，不影响任何原有判定 |
| 块内句对数超过 `MAX_REFINE_PAIRS = 25000` 就整块报成一处替换 | 这类块本来就不是"两版之间的差异"，逐句配对没有信息量 |

实测：同一对 PDF **9.2 秒**返回（其中 9.4 秒是那本书的文本抽取，diff 只花 0.1 秒），
`relation=distinct`、相似度 0.01%，界面顶上那行"它们可能根本不是同一篇文献"照常给出。

### 二、证据里的"原文"把连字符词读了两遍

`/api/papers/{id}/qa` 返回的每一条锚点，`source_text` 都是这样：

```
Self-attention, Self-attention, sometimes called intra-attention intra-attention is an …
```

PDF 原文并没有重复（`PyMuPDF` 抽出来的都是单份）。问题在 `text_index`：
一个原文词 `raw="Self-attention,"` 会被 `split_tokens` 切成 `self` / `attention`
两个 token，**两个 token 都存着整串 raw**，`_build_anchor` 直接 `" ".join(t.raw)`，
于是同一个词被拼了两遍。凡是带连字符的词（self-attention、intra-attention、O(n)）
全部中招，而这恰好是这篇论文里出现最多的词。

改法：`Token` 增加 `word_id`（同一个原文词切出的 token 共用一个编号），
回显时同一编号只拼一次。这类 bug 不报错、测试也不会挂 —— 只有人盯着证据读
才会发现"原文怎么怪怪的"。

### 三、重启服务遇上 arXiv 限流，推荐页还是白的

原来"上一次成功的批次"只放在内存里（15 分钟 TTL），进程一重启就没了。
把整批候选落盘到 `data/recommend_batch.json`（原子写，12 小时有效），
失败时的退路变成：内存缓存 → 落盘批次 → 空降级。

顺带修了文案：落盘那份可能存了五小时，`note` 里写"312 分钟前刷到"读着别扭，
过 90 分钟就换成"5 小时前刷到"。

```
GET /api/recommend?limit=6（冷启动）→ 200  2.06 s  12 条候选落盘
GET 同一条（命中缓存）             → 200  1.49 s  cached=true
```

全套 **361 项通过**（新增 9 项：推荐批次落盘/过期/损坏、句对预算、长度上界、
锚点回显）。

## E-018 · 扫描件 OCR：把「没有文字层的 PDF」变成能检索、能引用的文档

评分表里「多模态文档解析」占 7 分，测试用例 3.2 直接点名要一份扫描版论文
（`1706.03762v1_img.pdf`）。原来这条路径是断的：`page.get_text()` 返回空串，
解析链一路走到空白，用户只看到「解析失败」，连失败原因是"没有文字层"都不知道。

本地样本：`pdf/1706.03762v1_scan.pdf` —— 把原论文渲染成纯像素、文字层彻底抹掉，
15 页，sha256 `224e4915…fe6d2`（生成脚本 `scripts/make_scan_sample.py`）。
真值就用原始矢量版 `pdf/1706.03762v1.pdf` 的文字层，逐词对。

### 一、选引擎：RapidOCR 而不是 Tesseract

| 方案 | 装起来要什么 | 评委机器上的风险 |
|---|---|---|
| Tesseract | 另装可执行文件 + `chi_sim`/`eng` 语言包 | 装不上这条用例就是 0 分 |
| RapidOCR（PP-OCRv4 的 ONNX 版） | `uv sync` 一个纯 wheel | 跟着项目依赖一起装好 |

中英文同一个模型，不用挑语言参数。代价是 CPU 上慢，一页正文 6~9 秒。

### 二、分辨率不是越高越好：72 dpi 才是峰值

这是整轮实验里最反直觉的一条。把同一份扫描件在不同 dpi 下各认一遍，
第 1–5 页合计（`scripts/eval_ocr.py 5 <dpi>`）：

| dpi | 词级 F1 | 完全命中 | 召回 | 粘连（丢空格） | 认错 |
|---|---|---|---|---|---|
| 48 | 0.476 | 53.0% | 51.0% | 0.1% | 46.8% |
| 60 | 0.835 | 85.8% | 83.4% | 0.1% | 14.1% |
| **72** | **0.866** | **90.6%** | **85.8%** | **0.2%** | **9.2%** |
| 96 | 0.827 | 91.4% | 78.9% | 1.2% | 7.3% |
| 120 | 0.786 | 87.5% | 74.4% | 4.6% | 7.9% |
| 150 | 0.485 | 67.9% | 40.2% | 9.6% | 22.6% |
| 200 | 0.539 | 73.1% | 44.1% | 7.1% | 19.8% |

两条曲线都呈倒 U：低于 60 dpi 字糊成一团，高于 120 dpi 反而**掉得比低分辨率更狠**。
后半段的原因是模型行为，不是画面质量：PP-OCR 的识别分支会把每一行裁剪统一缩放到
48 px 高，原图越大、压缩比越狠，词间那一两个像素的空白最先被抹平，
于是 "we found it beneficial" 读成 "wefounditbeneficial" —— 一个谁都不认识的词。
粘连率随 dpi 单调上升（0.2% → 4.6% → 9.6%）正好印证这一点。

后来几页（参考文献、图表页，字号更小）复测，结论不变：
第 10–14 页 72 dpi 词级 F1 0.776 / 召回 80.0% / 粘连 1.0%，
120 dpi 只有 0.661 / 63.8% / 4.2%。

**为什么会选错**：一开始只量了字符相似度，而它几乎不随 dpi 变化（0.93 上下）——
字都认对了，只是粘在一起。粘起来的词在 BM25 索引里根本不存在，
检索查 "found" 永远命中不了 "wefound"，逐字引用更是全挂。
换成词级比对才看得见这个差别，所以 `eval_ocr.py` 现在同时打命中率、召回、粘连、F1。

### 三、试过但更差：从像素里找回空格

既然粘连是主要损失，最直接的思路是自己从行图片里找"空白列"重新切词
（墨迹投影法：沿水平方向统计每一列的黑点，低于阈值的列即为词边界）。
写了三版：固定阈值、按字高自适应阈值、以及把模型给出的空格与投影边界对齐取并集。
三版全部比直接用模型自己吐的空格差 —— 模型在 72 dpi 下本来就吐得挺准（粘连 0.2%），
再从像素里找边界只会把 "Transformer" 切成 "Trans" + "former"。
代码全部删掉，负结果记在 `_words_from_text` 的 docstring 里，免得以后有人再试一遍。

### 四、读序：三处必须自己收拾的坑

RapidOCR 返回的是检测框列表，**顺序是检测顺序，不是阅读顺序**。
双栏论文直接按 y 排会读成「左1 右1 左2 右2」，整篇文章的句子被打散。
用了 XY-cut：递归找"能把版面切开的空白缝"，横切优先，切不开再竖切。
三个真实事故：

1. **arXiv 投稿戳被当成正文**。论文左边距那个竖排的 "arXiv:1706.03762v1 [cs.CL]"
   被切成十几个碎块（"1"、"2"、"un"、"J"、"CL]"），它们在最左边，
   读序把它们排到正文前面，首页开头变成 "1 / 2 / un / J / 2 …"，标题被挤到十几行之后。
   修法：宽高比 < 2 的行（竖排/旋转文字）整行丢掉，单字符行也丢掉。
2. **四个作者读成乱序**。同一排作者基线差 0.6 pt，"按 y 再按 x"排出来是
   「Jakob、Noam、Ashish、Niki」。修法：先按行中心做容忍度聚类（容忍度取行高的 0.5），
   同一行内再按 x 排 —— 现在与 PDF 文字层顺序一致。
3. **通栏标题拦腰截断竖缝**。标题横跨两栏时整页找不到贯通的竖缝，只能退回按 y 排，
   两栏又交错。靠 XY-cut 先横切剥掉标题带解决。

### 五、速度：并发只有 1.5 倍，别按线程数估

15 页扫描件、冷缓存、同一台机器（16 物理核 / 32 逻辑核）：

| 方式 | 墙钟 |
|---|---|
| 串行（切块器逐页同步调用） | 176 s |
| `warm()` 4 路并发 | 117 s |
| `warm()` 2 路 | 124 s |
| `warm()` 6 路 | 170 s |
| `warm()` 8 路 | 109 s |

只有 ~1.5 倍，而且跑两遍能差一倍（这台机器时钟 2.4 GHz、16 核，
onnxruntime 一页之内就把核占满了，多页并发只是在抢同一批核）。
**不要按"线程数 × 加速比"去调这个参数**；4 路是稳妥值，再往上纯属碰运气。

顺带排掉的几个方向：`intra_op_num_threads` 调到 1/2/4/8、
`OMP_WAIT_POLICY=PASSIVE`、`cv2.setNumThreads(1)`、`Rec.rec_batch_num` ——
对墙钟的影响都在噪声范围内（同一页在不同会话里 4.6 s 和 13.9 s 都出现过）。
真正的大头是一页几十行文字要逐行跑识别分支，这是 CPU 上 PP-OCRv4 的固有成本。

### 六、磁盘缓存不是优化，是必需品

资料库每次启动都会把所有 PDF 重新切一遍（`registry._load_existing()`）。
库里只要有一份扫描件，**每次重启都要重跑两三分钟 OCR**，演示现场会被当成"服务挂了"。
所以识别结果按 `sha1(路径|大小|mtime|页码|dpi|缓存版本)` 落盘，
重启后 34.9 s → 0.09 s。缓存文件坏了就当没有、重新识别，不能让整份文档解析失败。

代价要说清楚：**缓存被清空后的第一次启动仍然很慢**。库里存着这份 15 页扫描件时，
冷启动要先把 15 页认完才肯监听端口，实测约三到四分钟。这在演示现场是个风险 ——
所以别在演示前删 `data/ocr_cache`，换机器/换容器时第一次启动要预留这段等待。

### 七、结果

上传接口实测：

```
POST /api/papers  file=1706.03762v1_scan.pdf   （无并发预热：2m39s）
POST /api/papers  file=1706.03762v1_scan.pdf   （warm 4 路：1m42s）
→ {"pages":15,"chunks":32,"duplicate_of":"0a9bff1be357",
   "relation":"related","similarity":0.1692}
```

（这两条是在默认还是 120 dpi 时量的，同口径可比；换成 72 dpi 后单页更快，
绝对值还要低一些。）

上传后问答，"What is multi-head attention and why is it used?" 七条结论
全部 `status=supported`、`exact=true`，锚点落在第 4 页真实坐标上
（模型每次生成的句子不完全一样；另一次运行里它改写了原句，其中一条被判 weak）：

```
"we found it beneficial to linearly project the queries, keys and values h times…"
"Multi-head attention allows the model to jointly attend to information from
 different representation subspaces at different positions."
```

换成 120 dpi 时，同样的锚点读出来是 "wefound it beneficial tolinearly project the
queries,keys andvaluesh times" —— 词粘成一坨，BM25 查 "found" 永远命中不了，
这就是 §2 那张表里「粘连率」这一列的代价。

也就是说：抗幻觉的逐字溯源在扫描件上照样成立。OCR 给出的坐标是识别框的坐标，
会和真实字形差几个像素（够画高亮，不够做精确测量），但「这段确实在原文里」
这个判断不受影响 —— 这正是 `text_index._page_words` 在文字层为空时改走 OCR 词流的原因。

顺带修了一处自相矛盾的提示。比对那条被改写过句子的结论时，界面打出来的是
「仅模糊命中（最低相似度 **1.00**），原文需人工确认」—— 两位小数把 0.99x 四舍五入成了
1.00，读者只会看到「相似度 1.00 却判 weak」。现在印四位再抹掉尾零
（`_format_similarity`），并加了用例钉住：判定和数字不许打架。

### 7.1 扫描件的章节树与参考文献：一遍跑下来才发现的三件事

把同一篇论文的文字版和扫描版并排比，差异全在「版面结构」而不是「文字」：

| 指标 | 文字版 | 修之前（扫描） | 修之后（扫描） |
|---|---|---|---|
| 章节条目 | 23 | 3（`Abstract` / `References` / 一条图表标签） | 20 |
| 参考文献条数 | 36 | **0** | 35 |
| 引用图谱出边 | 有 | 无 | 有 |

三处根因，都不在 OCR 引擎上：

1. **标题行被并进了正文**。OCR 的分块按行距猜，`References` 与上一段末尾行距只有
   12pt（页内正常行距 0~3pt，段间 9~20pt），于是并成 `…available soon. References`。
   切块器的关键词判据要求整块**只有**这个词，从此整份文献一条引文都抽不出来。
   现在识别时让"短行"（宽度 < 本页行宽 90 分位的 50%、≤5 词）**两头断开**独立成块。
   参考行宽必须用 90 分位而不是中位数：带插图的页面上图注和坐标轴标签又多又短，
   第 3 页的中位行宽只有 50pt（正文满行 397pt），中位数一低，阈值成了 20pt，
   整页没有一行够格。

2. **"字号"判标题这条规则在扫描件上必须停用**。`size` 是像素墨迹高度，取决于这一行
   有没有括号和上下伸的字母：实测同一份论文正文 13~19pt、真标题 13~20pt，两个区间
   几乎完全重叠。按 `正文 × 1.12` 判，一边漏掉大半真标题，一边把参考文献里的条目行
   （`[13] Zhongqiang Huang and Mary Harper…`）判成标题，整个 References 节被切成
   七八段。现在 OCR 块带 `size_proxy` 标记，字号规则直接跳过，改靠关键词与编号 ——
   而 OCR 常把编号和标题粘成一个词（`7Conclusion`、`3.2Attention`），所以对
   `size_proxy` 的块额外放宽"编号后必须有空格"，代价是尾巴必须 ≤6 词、且首字母大写
   （否则 `11 ion@google.com` 这种首页单位碎片也会中）。

3. **参考文献解析读的是原文页面，扫描件那里是空的**。`_page_blocks` 为了避开"切块从
   条目中间切一刀"而回原文读页面块，可扫描页的文字层是空的 —— 标题认出来了，
   读出来还是 0 条。现在它接的是同一个 OCR 钩子；而且 OCR 块按**行**拆开（文字层
   的块照旧整块），因为 OCR 会并块，而 `[n]` 标记必须顶到行首才认。这一条修完，
   35 条 vs 文字版 36 条（差的那条是 OCR 自己没识别出来的整行）。

全套 **405 项通过**（`test_scan.py` 19 项：判定/混合文档/引擎缺失降级/损坏文件
/竖排丢弃/单字符丢弃/同行排序/双栏读序/通栏标题/空格保留/墨迹高度/独立短行成块
/行宽 90 分位/落盘缓存/坏缓存容错/真实识别一次；表格与插图见 E-019）。

## E-019 · 表格与插图：把「非文字版面」还原成能检索的数据

评分表「多模态文档解析」7 分里，OCR 只解决了一半 —— 扫描件。另一半是**结构**：
表格和插图在切块器眼里从来不是"非文字版面"，而是"读顺序里的一段"。
Transformer 的 Table 2 被读成这样一段：

```
Model BLEU EN-DE EN-FR Training Cost (FLOPs) EN-DE EN-FR
ByteNet 23.75 39.2 GNMT + RL 24.6 39.92 ConvS2S 26.36 40.56 ...
```

问「Transformer 的 EN-FR BLEU 是多少」，检索命中这一段，模型看到的是一串
数字和它们上方的列名隔着七行 —— 说对了是运气。所以加了一层
`app/parsing/visuals.py`：`find_tables()` 给网格，单元格文字自己从
`get_text("words")` 里按坐标捞回来。

### 一、不能用 `table.extract()`

pymupdf 自带的 `extract()` 按**文本行**切单元格，而 `24.6` 在 PDF 里常常是
`246` + `.` 两个 text run。实测：`extract()` 给出 `246`、`.`；按坐标捞词再拼
才是 `24.6`。拼的时候还要判断"两个词之间要不要空格"：9pt 字体的词间空格实测
约 2pt，而小数点碎片之间的间距接近 0。阈值取 0.25 倍行高（≈2.25pt）时
`BLEU` 和 `EN-DE` 会被粘成 `BLEUEN-DE` —— 这是自己写的测试当场抓到的，
改成 0.12 倍行高（≈1.1pt）两头都分得开。

### 二、四个"看起来是表格"的东西

| 误判对象 | 长什么样 | 挡法 |
|---|---|---|
| 目录页 | GPT-3 的 Contents 被认成 32×3 的表：章节名和页码确实对齐 | 页面的 `......` 引导点 ≥3 处就整页跳过 |
| 论文首页 | 标题页的"作者 + 单位"本身就是两列对齐，认成 7×2，格子里全是人名 | 首页上抓不到表题的网格一律不要 |
| 图标与徽标 | 面积不到整页 2% 的嵌入位图 | 面积下限 |
| 扫描件整页位图 | 面积超过整页 80% 的那张"图"其实就是这一页 | 面积上限 |

### 三、`Table 2.1` 不是 `Table 2`

GPT-3 的表题是 `Table 2.1`、`Table 2.2`、`Table 3.1`……最初的正则只取 `\d+`，
于是八张不同的表在界面上全叫 "Table 2"、"Table 3"，看着像同一张表重复出现。
编号要连子号一起取。

### 四、booktabs 的表体会被认成一整格（两轮才修好）

只有三条横线、没有竖线的排法（GPT-3 全篇如此）里，`find_tables()` 只切出
"表头行 + 一整块表体"，10 个模型的数字全挤在一个格子里：

```
'125M 350M 760M 1.3B 2.7B 6.7B 13.0B 175.0B'   ← 拼成一串，模型名对不上
```

`extract()` 与 `strategy="text"` 都试过，网格切法完全一样 —— 问题不在策略，
在这个排法本身就没有逐行横线。

**第一轮**只是把格内换行留住（`\n`），前端 `white-space:pre-line`、Markdown
输出 `<br>`。看着能读了，但一测表就露馅：Transformer 的 Table 2 第一个模型
本来没有 EN-DE 值，格内少了那一行，于是后面每个数字都往上错一格 ——
把 `28.4` 读成 `ConvS2S` 的成绩。

**第二轮**改成按视觉行重建：一行内所有词按 y 聚成"线"，每条线再按列的 x
范围分配，**缺值的格子留空**。`_visual_rows()` 就是这么来的。效果：

| 表 | 修前 | 修后 | 原文 |
|---|---|---|---|
| Transformer Table 2 | 5 行 × 4 列（整块表体挤一格） | 11 行 × 4 列 | 11 行 |
| GPT-3 Table 2.1 | 2 行 × 8 列 | 9 行 × 8 列 | 9 行 |

`GPT-3 175B` 那一行现在读出来是 `175.0B | 96 | 12288 | 96 | 128 | 3.2M | 0.6×10⁻⁴`
—— 问"175B 有几层"能直接从表里答，不再靠模型从上下文猜。
有合并单元格（`row.cells` 里是 None）的行拼不出视觉行，退回逐格拼接而不是猜。

还剩一个没解决的：跨行合并的标签（Transformer 的 Table 3 里 `base`、`(A)`、
`(B)` 只写一次、纵向居中）会被分到其中一行，其余行那一格是空的 ——
往前填充又会把"这一格本来就是空值"误判成"沿用上一行"，所以宁可不填。

### 五、开销：40 页是"点一下等得住"的上限

`find_tables()` 实测约 0.29 秒/页。所以只解析前 `MAX_ANALYZE_PAGES = 40` 页，
结果落盘（键含文件大小、mtime、页数上限、缓存版本），同一份 PDF 只算一次。

| 文献 | 页数 | 首次解析 | 命中缓存 | 表格 | 插图 |
|---|---|---|---|---|---|
| Attention Is All You Need（矢量版） | 15 | 3.2 s | 0.00 s | 4 | 2 |
| Language Models are Few-Shot Learners | 75 | 10.6 s（前 40 页） | 0.00 s | 16 | 21 |
| Understanding Deep Learning（教材） | 541 | 6.8 s（前 40 页） | 0.00 s | 0 | 14 |
| Attention（扫描件） | 15 | 0.02 s | — | 0 | 0 |

教材那份**前 40 页确实一张表都没有**（逐页搜 `Table N` 为 0）—— 不是漏抽。
扫描件是另一回事：扫描页没有文字层，`find_tables()` 一律返回空，所以这条路上
的结论是**空结果 + 说明**（"前 15 页里有 15 页是扫描页……这份 PDF 提不出图表"），
不是 500，也不是猜一张网格出来。

### 六、Agent 也要能读到表格

光有界面不够：问答链路的证据仍然是切块后的行，"175B 有几层"照样靠猜。
所以 `find_tables` 成了第 10 个 Agent 工具 —— 入参 `paper_id` 加可选 `keyword`，
返回还原后的格子，**命中行一律带上表头**（只给 `GPT-3 175B | 96`，谁也看不出
96 是层数）。扫描件在这里同样是"空结果 + 说明"，不是异常。

### 七、测试（21 项）

`test_visuals.py` 16 项：行列与数字归属、表题在上/图题在下、续行合并、
Markdown 分隔行与 `<br>`、缩略图是真 PNG、越界返回 None 不抛异常、
扫描件如实说明、磁盘缓存复用、坏缓存重解析、目录页挡掉、首页作者块挡掉、
子号保留、格内分行、缺值留空不错位、合并单元格退回逐格拼接。
其中三条直接测 `_cell_text` / `_visual_rows` 而不是造 PDF：GPT-3 与
Transformer 的那两种排法（无框线、缺值）用 `insert_text` 造不准，
`find_tables()` 会按文字行自己切。
`test_visuals_api.py` 5 项：三条端点各守一件事，外加越界索引与不存在的文献。
`test_agent.py` 另加 2 项：命中行带表头、扫描件说清原因而不是报错。

## E-020 · 第一次真机部署：三个只有「从零跑一遍」才会露头的问题

本地能跑、单测全绿，不代表换一台机器能起。2026-11-07 把项目部署到
阿里云 ECS（Ubuntu 22.04 / 2 vCPU / 4 GiB）时，连撞三次，每一次都不是代码逻辑错，
而是**环境假设错**。记下来，因为它们全都会被下一个人重踩。

### 一、`--exclude='.env.*'` 把 `.env.example` 一起排掉了

打包脚本原本写着

```bash
tar czf - --exclude='.git' --exclude='.env' --exclude='.env.*' ...
```

意图是「密钥文件别上传」。但 `*.` 通配符不区分 `.env` 和 `.env.example`，
结果 `.env.example` 也进了排除名单。远端第 3 步 `cp .env.example .env` 直接
`cannot stat`，脚本 exit 1。

**修**：只留 `--exclude='.env'`，它按整名匹配，不会连累 `.env.example`。

### 二、`mkswap -q` 在 Ubuntu 22.04 上不存在

```console
$ mkswap -q /swapfile
mkswap: invalid option -- 'q'
```

`-q/--quiet` 是较新 util-linux（2.38+）才有的；22.04 带的是 2.37。
更麻烦的是：`fallocate && chmod && mkswap && swapon` 这一串里 mkswap 失败后，
脚本**没有停在原地**，而是继续打印「已加 2 GB swap」—— 文件建了、fstab 写了、
swap 实际没启用。正好是「以为做完了"最危险的那种状态。

**修**：去掉 `-q`，`mkswap` 与 `swapon` 拆成两条，最后用
`swapon --show=SIZE --noheadings` **回读**确认，而不是打印一句预期结果。

### 三、`/app/data` 权限：容器一直 `Restarting`

服务起来后立刻进入重启循环：

```
File "/app/apps/api/app/api/registry.py", line 191, in __init__
  self.store_dir.mkdir(parents=True, exist_ok=True)
PermissionError: [Errno 13] Permission denied: '/app/data/papers'
```

镜像里已经 `mkdir -p /app/data/papers && chown -R appuser:appuser /app/data`，
Dockerfile 这一步是对的。**但 `./data:/app/data` 是 bind mount —— 镜像里那个目录
在运行期被宿主机目录整个盖住**，镜像里的属主设置一点用都没有。宿主机上
`data/` 是 root 建的，容器内是 uid 10001，`mkdir` 必然被拒。

**修**：起服务前在宿主机上 `mkdir -p data/papers && chown -R 10001:10001 data`，
已写进 `scripts/deploy_remote.sh` 与 `docs/DEPLOY.md` 第 5 步。

这条的教训最值钱：**镜像里对挂载点的 `chown` 是无效的**。要么在宿主机侧设属主，
要么让入口脚本以 root 起步、chown 之后再降权 —— 后者与"非 root 运行"的取舍不划算，
这里选了前者。

### 四、顺带记一笔：构建时间不是 3–6 分钟，是 13 分钟

Dockerfile 里 `apt-get install libgomp1` 那一步：

```
Fetched 10.1 MB in 12min 11s (13.8 kB/s)
```

`deb.debian.org` 在国内只有十几 kB/s。依赖安装（`uv sync`）反而只用 18 秒 ——
因为它走的是清华源。**留给下一个人**：要么给 Dockerfile 的 apt 也换 `[mirrors.aliyun.com]`
源，要么接受首次构建十几分钟；重跑时这一层有缓存，不受影响。

### 五、`docker compose restart` 不会重读 `.env`

填完 key 后按常识 `docker compose restart api`，健康检查依旧
`llm_configured: false`。容器的环境变量是**创建时**从 `env_file` 灌进去的，
`restart` 只是重启同一个容器、沿用旧环境；`start`/`stop` 同理。
要重新读 `.env` 必须重建容器：

```bash
docker compose up -d --force-recreate api
```

重建后立刻 `llm_configured: true`，`docker compose exec -T api python -c ...`
读到的 key 长度 35、前缀 `sk-`，与写入值一致。

**这条对演示现场很要命**：如果只在 `.env` 里改了 key 再 `restart`，界面表现
是"问答一直降级"，很容易被误判成 DeepSeek 服务挂了、网络不通，而真正原因
只是容器没重建。已把 `scripts/deploy_remote.sh` 结尾的提示和 `DEPLOY.md`
第 7 节全部改成 `--force-recreate`。

### 结果

| 项 | 状态 |
|---|---|
| `/api/health`（服务器内部） | `{"ok":true,"papers":3,"llm_configured":true}` |
| LLM 密钥 | 已配（35 字符，走 stdin 传入，未经过命令行参数、未落本机临时文件、未打印） |
| 入库文献 | Attention Is All You Need / BERT / GPT-3，共 9.4 MB 落在 `data/` |
| 容器状态 | `Up (healthy)`，非 root，端口 `0.0.0.0:8017` |
| 公网访问 | 安全组放行 8017 后全通：`/` 200/194 KB（0.09 s）、`/api/health` 200、`/docs` 200 |
| 端到端问答（公网） | 问「几个注意力头」→ 答「h = 8」，逐字命中第 5 页，`exact:true`、`similarity:1.0` |
| swap | 2 GiB 已启用并回读确认 |
| 代码上传 | 1.07 MB，`.env` / `data` / `models` / `pdf` / `.git` 均未出本机 |

三处修复全部落在仓库里（`scripts/deploy_remote.sh`、`docker-compose.yml` 注释、
`docs/DEPLOY.md`），**不是手工在服务器上打补丁** —— 手工补丁换个机器就没了。

## E-021 · 上线之后才露头的三件事：OCR 缺系统库、chunked 读坏、apt 卡死

E-020 把服务跑起来之后，界面上有三个功能是「点得动、但结果是空的」。
三个问题的共同点：**本地开发环境全绿，只有真机容器里才复现**。

### 一、OCR：镜像里装了 rapidocr，却报「本机没有可用的 OCR 引擎」

上传扫描件返回 422：

```
共 15 页，其中 15 页缺少文字层，本机没有可用的 OCR 引擎…
```

但 `rapidocr-onnxruntime` 明明在 `pyproject.toml` 的主依赖里，也装进了 `.venv`。
进容器直接 import，真正的错误是：

```
File "/app/.venv/lib/python3.11/site-packages/cv2/__init__.py", line 153, in bootstrap
ImportError: libxcb.so.1: cannot open shared object file: No such file or directory
```

OpenCV 需要 `libGL.so.1` / `libxcb.so.1`，`python:3.11-slim` 一个都没有。
业务层把 ImportError 统一当成「没装 OCR」，于是错误信息指向了错误的方向 ——
**这比崩溃更难查：崩溃有栈，降级只有一句话。**

修法（`Dockerfile` runtime 层）：

```dockerfile
RUN apt-get update \
    && apt-get install -y --no-install-recommends \
        libgomp1 libgl1 libglib2.0-0 libxcb1 \
    && rm -rf /var/lib/apt/lists/*
```

修完实测：`import cv2` → 5.0.0；扫描件入库 15 页 24 块，**OCR 全篇 + 建索引 + 入库 72.6 秒**
（2 vCPU / 4 GiB，约 4.8 秒一页）。

### 二、多源检索：5 个站里 2 个永远「解压失败」

界面上写的是「OpenAlex、Semantic Scholar、Zenodo 暂不可用」，其中两条原文是：

```
OpenAlex（Error -3 while decompressing data: invalid code lengths set）
Zenodo（Error -3 while decompressing data: invalid code lengths set）
```

在同一台机器上直接 `urllib` 请求同一批 URL，**完全正常**；走 `net.fetch_bytes` 就必挂，
且每次必挂、换协议也不变 —— 说明不是网络抖动。差异只有一个：

```python
data = response.read((max_bytes + 1) if max_bytes is not None else -1)   # 旧代码
```

`amt=-1` 在 chunked 响应上是**错的**。`http.client` 只有在 `amt is None` 时才走
「剥掉分块框架、读完整个流」的正规路径；`amt=-1` 会命中 `amt <= chunk_left` 分支，
先读满第一个 chunk，再用 `_safe_read(-1)` 把剩余裸字节（后续 chunk 的长度行、CRLF）
一起吞进来。体里插进了框架字节，gzip 解压必然报 `Error -3`。

只有 OpenAlex 和 Zenodo 中招，因为它们**走 chunked 且不发 `Content-Length`**；
Crossref 带 `Content-Length`，一直正常。

修法一行：

```python
data = response.read() if max_bytes is None else response.read(max_bytes + 1)
```

**为什么本地 405 个测试一个都没拦住**：测试里的假响应是 `io.BytesIO`，
它的 `read(-1)` 乖乖读完全部；本机 venv 是 Python 3.12，而 3.12 的 `_read_chunked`
开头已经补了 `if amt is not None and amt < 0: amt = None`（上游修复），
镜像用的却是 `python:3.11-slim`。**版本差一个字，行为天差地别。**

补的三条测试（`tests/test_net.py`）：
起一个真的 `ThreadingHTTPServer` 回 chunked 响应，断言完整读回；
另外两条直接盯 `read` 的实参（`[None]` / `[max_bytes + 1]`），不依赖解释器版本。
把新代码改回 `read(-1)`，`test_read_is_called_with_no_amount_when_there_is_no_limit`
立刻变红 —— 验证过它会咬人，不是摆设。

修完实测：OpenAlex 67 046 字节、Zenodo 22 751 字节，两个源都回来了；
界面从「85 条结果 · 2 个来源可用」变成「4 个来源可用」（Semantic Scholar 仍按预期限流）。

### 三、`apt-get update` 卡 18 分钟，0% CPU

给镜像补 OpenCV 系统库，`apt-get update` 从 16:13 跑到 16:31 一直没动静，
`ps` 里 0% CPU、负载 0.00 —— 不是慢，是在等。同一台机器上量三个源：

| 源 | 同一份 `Release` 文件 |
|---|---|
| `deb.debian.org` | 31 KB/s |
| `mirrors.tuna.tsinghua.edu.cn` | 82 KB/s |
| `mirrors.aliyun.com` | **3.0 MB/s** |

差 96 倍。修法是在 runtime 层换源（`ARG DEBIAN_MIRROR` 可覆盖，默认阿里云）：

```dockerfile
RUN for f in /etc/apt/sources.list.d/debian.sources /etc/apt/sources.list; do
        [ -f "$f" ] && sed -i "s|http://deb.debian.org/debian|${DEBIAN_MIRROR}|g" "$f";
    done; true
```

换源后同一次构建从「13 分钟且经常卡死」降到 6 分钟。

### 结果

| 项 | 修之前 | 修之后 |
|---|---|---|
| 扫描件上传 | 422「本机没有可用的 OCR 引擎」 | 201，15 页 / 24 块，72.6 秒 |
| 扫描件问答 | — | 答「3.5 天 / 300,000 步」，三条结论回溯 p.7、p.7、p.1，逐字命中 |
| OpenAlex / Zenodo | 两个源必挂（gzip 解压失败） | 都正常返回 |
| 多源检索 | 43 条 · 2 个来源 | 85 条 · 4 个来源 |
| 构建耗时 | 13 分钟，`apt` 可能挂死 | 6 分钟 |
| 单元测试 | 405 | 409（+4，其中 1 条能咬住这个 bug） |

三处修复依旧全部落在仓库里（`Dockerfile`、`apps/api/app/tools/net.py`、
`apps/api/tests/test_net.py`、`docs/DEPLOY.md`），服务器上没有手工补丁。

## E-022 · 录演示视频时才看见的六件事：扫描件在库里没有名字

录视频时为了走「多模态 + 版本谱系」这条线，往库里传了一份 `1706.03762v1` 的扫描件。
录完回看画面，才注意到屏幕上有一串说不通的地方 —— 单测全绿，因为它们测的是
"每块砖砌得直不直"，没人测"整面墙看着歪不歪"。

### 症状（都是画面上一眼可见的）

1. 文献库里那行叫 `1706.03762v1_scan`，日期写"日期未知"；
2. 进"版本谱系"，默认对是**BERT ↔ 扫描件**，关系"不同论文 · 0.3%" —— 拿两篇无关的论文对齐；
3. 改成「v7 ↔ 扫描件」后，结论是"删除 50 句、新增 0"；
4. 扫描件问答的引文是 `For each of these we use d d, dode/h 64.` 这种 OCR 残渣，界面上没有任何提示；
5. 问一个库里根本没有的问题，统计行写「通过 0 · 待确认 0 · 拦截 0」—— 读起来像护栏完全没工作；
6. 多源检索里 Semantic Scholar 那格写「未配 SEMANTIC_SCHOLAR_API_KEY」，看不懂也不告诉你怎么修。

### 根因（六条其实只有四个）

| 症状 | 根因 |
|---|---|
| 1 | `_title_from_layout` 只读首页的**文本层**；扫描件一个字都抽不出来，一路掉到文件名兜底 |
| 2 | 版本下拉按 `normTitle(title)` 分组；标题是文件名，分不到一组，退回"随便挑两篇" |
| 3 | `load_sentences` 同样只读文本层；扫描件读成空串，于是另一版的每一句都成了"新增" |
| 4 | 接口没把"这份是扫描件"这件事告诉前端，引文与索引完全自洽，没人在意"索引本身是 OCR 出来的" |
| 5 | 统计行的模板假设"一定有结论"，0 条结论时三个 0 拼出来反而是种误导 |
| 6 | 报错文案只报状态、不报出路 |

排序还有一层独立问题：**新旧曾经按"PDF 生成日期 → 上传时间"判**。扫描件没有元数据日期，
于是退回上传时间 —— 后传的 v1 被判成更新的那版，整份 diff 方向反了。
而 arXiv 的 `vN` 是作者发版时自己打的，对同一篇论文来说才是最硬的依据。

### 修法

**标题（扫描件）**：`_title_from_layout` 抽不到 span 时退到 `_title_from_ocr`。
不能照搬"字号最大就是标题"—— OCR 的 `size` 是行高像素当量，实测首页上
`nikip@google.com` 那行（19）比标题（16）还大。稳定判据换成**版面宽度 + 居中**：
首页上半部分最宽、且和第一行共用中轴线的那行。OCR 还会吃掉空格
（`AttentionIsAllYouNeed`），只在整行一个空格都没有时按驼峰断词补回来。

**分组**：优先用 `arxiv_id` 分组，没有才退回标题。arXiv 号是精确标识，
OCR 差一个连字符也照样分得进一组。

**新旧**：抽出共用的 `order_versions()`（arXiv 版本号 → 生成日期 → 上传时间），
HTTP 接口和 Agent 工具共用一份 —— 之前各写一遍，扫描件在两条路上判出的新旧是相反的。
响应里带 `order_by`，前端照实说"是按版本号排的"还是"只是按上传时间排的"。

**对比**：`load_sentences` 遇到没有文字层的页退到 `scan.ocr_lines()`（切块时已识别，基本是缓存命中）。

**出处**：`/qa` 与流式 `done` 事件都带 `scanned`，前端在结论上方注明"引文来自 OCR"。

### 结果（线上实测，同一对文件）

| 项 | 修之前 | 修之后 |
|---|---|---|
| 扫描件标题 | `1706.03762v1_scan` | `Attention Is All You Need` |
| 版本谱系默认对 | BERT ↔ 扫描件（不同论文 · 0.3%） | 扫描件 v1 → 文本版 v7（同一篇 · 40.0%） |
| 新旧依据 | 上传时间（方向反了） | `order_by=arxiv_version` |
| 逐句对齐 | 新增 50 · 删除 0 · 改写 0 · 忽略 0 | 新增 25 · 删除 15 · 改写 25 · **忽略 110** |
| 对齐耗时 | 1.0 秒 | 1.0 秒（OCR 走磁盘缓存，没有变慢） |
| 扫描件问答 | 引文残渣无提示 | 结论上方标注"正文与引文都来自 OCR 识别" |
| 0 结论时的统计行 | `通过 0 · 待确认 0 · 拦截 0` | `没有生成结论 · 校验环节无输入` |
| Semantic Scholar 失败 | `限流（未配 SEMANTIC_SCHOLAR_API_KEY）` | `限流（429）：未配 key，公共配额已被占满；配 key 后为 1 次/秒` |
| 单元测试 | 409 | 420（+11，覆盖标题/版本号/排序/扫描页对齐/出处标记） |

### 没修的那一件事，以及为什么

扫描件的「图表」标签仍然是 0 张。OCR 重建表格**能写，但这份样本上写不好**：
扫描件第 4 页有 Table 1，`find_tables()` 返回 0 张（整页是位图），
OCR 在那一带只认出表头一行 `Scaled Dot-Product Attention / Multi-Head Attention`，
表体数字一个都没出来。用这种输入去"重建表格"，输出的只会是一张假表。
所以界面保持"跳过 N 页扫描页（没有文字层）"的坦白说法，
把 OCR 表格提取留到有更好的版面分析模型时再做。

## E-023 · 再点一轮：三处"同一篇被当成两篇"，外加编号跳号

这一轮全程用**模拟点击驱动线上站**（`http://101.37.190.214:8017/`），
不靠读代码猜：每一条都是屏幕上真出现过的字。单测依旧全绿 —— 因为单测里的
语料只有一篇论文的一份文件，"同一篇存了三版"这种真实库会有的形态，
没有一条用例摆得出来。

### 症状

1. 综述页写「本次用到 **5 篇**：《Attention Is All You Need》（2 个版本）…」——
   库里确实只有 4 篇不同的工作，名额被同一篇的 v1、v7 各吃一格；
2. 综述引用的第 [1] 条来自 v1 扫描件，引文是 OCR 残渣
   `ndno ue o sued neaa joos e pu nb e uddeu se pqusp que uoun uoue uy`；
3. 写作 Copilot 引 FSA 第 12 页一条**书目**当证据：
   `tutorials/06-fused-attention.html, 2024. Ashish Vaswani, … Attention is all you need`；
4. Copilot 的引用列表编号是 `[1] [2] [3] [5] [6]` —— 凭空少一个号；
5. 上传撞版本时提示"库中已有版本较新"，依据是 **PDF 导出日期**；
   而同一对文件在版本谱系页被标成"按 arXiv 版本号排序"。两页口径不同，
   就存在给出相反结论的版本组合；
6. arXiv 入库按钮按下后 5 分钟没有任何文字变化（其实是服务器到 arXiv 只有约
   20 KB/s，4.5 MB 的 PDF 要等 328 秒）；
7. 中英对照的段落下拉里出现两行**完全同名**的选项（扫描件的 References 跨页被切开）；
8. 任务 Agent 偶发"规划完了却没有结论"。

### 根因

| 症状 | 根因 |
|---|---|
| 1 | `collect_evidence` 按**文件**给检索预算，不按**工作**；同一标题的多个版本各占一格 |
| 2 | 版本多的时候，检索分最高的那一格恰好是扫描件 —— 分数只看词频，不看这份正文是不是 OCR 出来的 |
| 3 | 综述的 `_search` 有一道"引文列表不当证据"的过滤（`is_reference_list`），**Copilot 没有** |
| 4 | `references` 只收被引用的编号，却沿用原证据号；未被引用的号就成了空档 |
| 5 | `recommend_version` 自己写了一遍"谁更新"：只看 `created_at`，而 `order_versions` 早就按"版本号 → 日期 → 上传时间"三级判过 |
| 6 | 前端只在**结束**时改一次按钮文案，中途没有任何进度 |
| 7 | 下拉标签是「节名 · 页」，扫描件的同一页被切出两块，标签自然撞车 |
| 8 | DeepSeek 偶尔在**一次回复里吐两个 JSON 对象**，`json.loads` 整串解析报 `Expecting ',' delimiter`，任务 Agent 判定"决策失败"退回预设计划 |

### 修法

- **一篇只占一格**：新增 `app/rag/works.py::one_version_per_work()`，
  综述与 Copilot 两个检索入口共用。留哪一版按
  「不是扫描件 → 版本号高 → 导出日期新 → id 定序」，
  第一条就是为了不把 OCR 错字当"作者原话"引用。
- **证据过滤只有一份**：`app/rag/evidence.py` 收走 `is_reference_list` /
  `is_front_matter` / `body_chunks`，Copilot 的兜底也从"首块"（常常是作者名单）
  换成"第一块正文"。
- **引用重新编号**：`references` 收完被引用集合后重排成 `1..K`，要点里的编号同步重映射
  —— 回链靠 `paper_id + page`，不依赖编号，重排是安全的。
- **判新旧只剩一套**：`recommend_version` 改成调用 `order_versions`，
  并把**依据**一起返回（`recommendation_by`），前端照着说
  "版本号更高"还是"PDF 生成日期更晚"——同一个建议用错依据就是假话。
- **arXiv 入库有进度**：每秒钟改一次按钮（`下载中 12s…`），20 秒后补一句
  说清"这台服务器到 arXiv 只有约 20 KB/s，几 MB 要等两三分钟"。
- **块名撞车补序号**：同一标签出现多次时追加 `· 1/2`、`· 2/2`。
- **两个 JSON 对象**：`first_json_object()` 用 `JSONDecoder.raw_decode` 从头扫，
  取第一个完整对象，后面的多余内容丢弃。

### 结果（线上实测）

| 项 | 修之前 | 修之后 |
|---|---|---|
| 综述的 6 个名额怎么分（库内 5 篇工作 / 6 个文件） | 2 个名额给了同一篇（v1 扫描件 + v7） | 一个名额一篇工作，同一篇只用 v7 |

## E-024 · 「生成日期未知」不是解析坏了：arXiv 换了 GenPDF

### 现象（点着点着发现的）

文献库里 FSA 那一行写着：

```
FSA: AN ALTERNATIVE EFFICIENT IMPLEMENTATION / 2508.18224.pdf · 生成日期未知
```

两处不对劲：日期是空的，标题还是全大写。而库里 7 份文件里只有 2 份没有日期
（另一份是扫描件，没文本层情有可原），偏偏是最新的那篇没有。

### 量数据：PDF 里到底有没有这个字段

直接进容器，对 `/app/data/papers/a3352442cd37.pdf` 读元数据：

| 字段 | 值 |
|---|---|
| `creationDate` | `''`（空串） |
| `modDate` | `''`（空串） |
| `producer` | `pikepdf 8.15.1` |
| `creator` | `arXiv GenPDF (tex2pdf:a6404ea)` |

同一份 PDF 第 1 页的投稿戳：

```
arXiv:2508.18224v3  [cs.DC]  1 Jul 2026
```

### 根因

arXiv 从 2025 年起改用 GenPDF（pikepdf）重新出片，**导出时不再写
`creationDate` / `modDate`**。`_pdf_date()` 取不到就返回空串 —— 这个行为是对的，
不是解析 bug：文件里真的没有这个字段，硬编一个日期才是造假。

但界面只有一句「生成日期未知」，用户看到的是"系统坏了"，而不是"这份 PDF 本来就没写"。
而首页那行戳上其实印着日期，只是它说的是**"这一版什么时候投到 arXiv"**，
不等于 `created_at`（"这份 PDF 什么时候导出的"）。两个概念不能混成一句话。

标题的问题同理：ICLR 模板把标题排成全大写，版面抽取忠实照抄，
于是库里一排论文像在喊。而 PDF 元数据里恰好是正常大小写。

### 修法

- **日期另立一栏**：`Paper.arxiv_date`，从首页投稿戳取（`arXiv:…vN [分类] 1 Jul 2026`），
  写进 sidecar；老 sidecar 启动时回填，不用重传。
- **措辞分开**：有 `created_at` 写「PDF 生成于 …」，只有投稿日期写「arXiv 投稿于 …」，
  两样都没有才写「生成日期未知」。库行、阅读器、版本谱系侧标、上传冲突提示四处统一走
  `paperDateLong()` / `paperDateShort()`。
- **不用它判新旧**：`order_versions()` 里明确不引入 `arxiv_date` ——
  一边有导出日期、一边只有投稿日期，等于拿两种时间比先后，
  更要紧的是这一层的结论会被上传页拿去建议"删哪一份"。凭半份证据劝人删文件，
  比老实说"判不出来"危险得多。
- **标题只换大小写、不换字**：`_prefer_meta_casing()` 仅在版面标题全大写、
  且元数据标题压平（去标点、转小写）后**逐字相同**时采用元数据的写法。
  元数据标题本身不可信（1706.03762v7 的 metadata title 是 `scholarly works.`），
  逐字比对正好把那类坑挡在外面。
- **`TITLE_SCHEMA` 2 → 3**：不涨版本号，老 sidecar 里存着的全大写标题永远不会重算 ——
  代码修好了，库里那一行还是老样子。

### 结果（线上实测）

| 项 | 修之前 | 修之后 |
|---|---|---|
| 库行（FSA） | `2508.18224.pdf · 生成日期未知` | `2508.18224.pdf · arXiv 投稿于 2026-07-01` |
| 库行标题 | `FSA: AN ALTERNATIVE EFFICIENT IMPLEMENTATION…` | `FSA: An Alternative Efficient Implementation…` |
| 阅读器信息行 | `21 页 · 42 块 · v3` | `21 页 · 42 块 · v3 · arXiv 投稿于 2026-07-01` |
| 版本谱系侧标 | 只有 `v3 · 21 页` | `v3 · arXiv 2026-07-01 · 21 页` |
| 有导出日期的论文 | `PDF 生成于 2024-04-02` | 不变（投稿日期不去顶替它） |
| 扫描件 v1 | `生成日期未知` | 不变（真没有日期，就该这么写） |
| 单元测试 | 437 | 439（+2：戳日期解析 / 全大写标题取元数据写法） |

### 记一笔

- 这事最容易误判成"解析器坏了"，先去查数据再改代码 —— 元数据里两个空串摆在那里，
  想当然去"补一个日期"就变成了编数据。
- 同一份 PDF 里，`created_at`（导出时间）和 `arxiv_date`（投稿时间）差了 1–2 天是常态，
  序号不同不等于哪个错了。混写过一次就会让"哪版更新"的结论自相矛盾。
